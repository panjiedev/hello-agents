> 一句话概括：**A2A 基础篇手写的"翻译官"变成框架自带的 `A2ATool` 一行导入，三个文件依次演示：最小接入、智能客服实战、以及超越"一问一答"的 Agent 间协商。**

## 🧅 第一层（最外层）：这组文件在干什么？

基础篇的 `09_A2A_WithAgent.py` 花了近 40 行手写 `A2ATool` 类，把远程 Agent 翻译成本地工具。HelloAgents 框架把这层翻译收编成了内置工具：`from hello_agents.tools import A2ATool`。本篇三个文件就是这个内置工具的三级应用：

| 文件 | 场景 | 复杂度 |
|---|---|---|
| `10_A2ATool_Simple.py` | 一个协调者连一个研究员 | 最小可用示例 |
| `10_CustomerService.py` | 接待员 + 技术专家 + 销售顾问 | 完整业务闭环（对应书中 10.3.4 实战案例） |
| `10_AgentNegotiation.py` | 两个 Agent 讨价还价 | 协商模式：提案 → 评估 → 还价 |

## 🧅 第二层：`10_A2ATool_Simple.py`——三行完成接入

去掉导入和注释，核心只有（第 16-24 行）：

```python
coordinator = SimpleAgent(name="协调者", llm=llm)

researcher_tool = A2ATool(agent_url="http://localhost:5000")
coordinator.add_tool(researcher_tool)

response = coordinator.run("使用a2a工具，向Agent提问：请研究AI在教育领域的应用")
```

对比基础篇的手写版本：`ToolParameter` 定义、`execute_skill` 拼消息、`result` 字典拆包——全都消失了，只剩一个 `agent_url`。注释里点了一句用法（第 23 行）：内置 A2ATool 用 `action="ask"` 向远端 Agent 提问，所以提示词里写"向 Agent 提问：……"就能触发。

前提是 5000 端口有个研究员 Agent 在跑（就是 `09_A2A_Server.py`）——这个文件故意不自己起服务，强调**客户端与服务端的生命周期是独立的**：Agent 服务常驻，消费者随来随走。

## 🧅 第三层：`10_CustomerService.py`——智能客服的完整闭环

这是 A2A 应用的标准架构图，一个文件浓缩三层：

**后端专家层**（第 17-41 行）——两个 A2A 服务，各带一个 `answer` 技能：

```python
tech_expert = A2AServer(name="tech_expert", description="技术专家，回答技术问题")

@tech_expert.skill("answer")
def answer_tech_question(text: str) -> str:
    match = re.search(r'answer\s+(.+)', text, re.IGNORECASE)
    question = match.group(1).strip() if match else text
    # 实际应用中，这里会调用LLM或知识库
    return f"技术回答：关于'{question}'，我建议您查看我们的技术文档..."
```

注释（第 27 行）明说了教学简化：真实系统里技能内部会再调 LLM 或知识库——**技能函数是任意 Python 代码**，里面套一个完整的 RAG 系统也完全合法。

**服务启动层**（第 44-46 行）——老配方，daemon 线程 + `time.sleep(2)` 等待就绪：

```python
threading.Thread(target=lambda: tech_expert.run(port=6000), daemon=True).start()
threading.Thread(target=lambda: sales_advisor.run(port=6001), daemon=True).start()
time.sleep(2)
```

**前台路由层**（第 49-74 行）——接待员 SimpleAgent 挂两个 A2ATool：

```python
receptionist = SimpleAgent(
    name="接待员", llm=llm,
    system_prompt="""你是客服接待员，负责：
1. 分析客户问题类型（技术问题 or 销售问题）
2. 将问题转发给相应的专家
3. 整理专家的回答并返回给客户"""
)

tech_tool = A2ATool(agent_url="http://localhost:6000",
                    name="tech_expert", description="技术专家，回答技术相关问题")
receptionist.add_tool(tech_tool)
sales_tool = A2ATool(agent_url="http://localhost:6001",
                     name="sales_advisor", description="销售顾问，回答价格、购买相关问题")
receptionist.add_tool(sales_tool)
```

路由逻辑在哪？不在任何 if/else 里——**在两个工具的 `description` 里**。LLM 读到"你们的 API 如何调用？"（第 86 行）时，对照"技术相关"和"价格、购买相关"两段描述自行分诊。想加一个"售后专家"？起一个新 A2AServer、加一个 A2ATool，接待员的代码零改动。这就是用协议+LLM 做路由相对于规则引擎的扩展性优势。

## 🧅 第四层：`10_AgentNegotiation.py`——从"问答"到"谈判"

前面的模式都是单向的：问 → 答。协商（Negotiation）引入了**有条件的拒绝与还价**。agent2 发起提案（第 49-64 行）：

```python
@agent2.skill("negotiate")
def negotiate_task(text: str) -> str:
    match = re.search(r'negotiate\s+task:(.+?)\s+deadline:(\d+)', text, re.IGNORECASE)
    if match:
        task = match.group(1).strip()
        deadline = int(match.group(2))
        proposal = {"task": task, "deadline": deadline}
        return str({"status": "negotiating", "proposal": proposal})
```

消息格式升级了：不再是自由文本，而是 `negotiate task:开发新功能 deadline:5` 这样**带字段的结构化文本**，正则按字段抽取。协商这种多轮、有状态的交互，对消息格式的严格性要求显著高于一次性问答。

## 🧅 洋葱心：提案评估的决策分支（`10_AgentNegotiation.py` 第 27-40 行）

```python
proposal = eval(proposal_str)
task = proposal.get("task")
deadline = proposal.get("deadline")

# 评估提案
if deadline >= 7:  # 至少需要7天
    result = {"accepted": True, "message": "接受提案"}
else:
    result = {
        "accepted": False,
        "message": "时间太紧",
        "counter_proposal": {"deadline": 7}
    }
return str(result)
```

这十行是整个协商协议的心脏，三个字段构成了完整的协商语义：

- **`accepted`**——布尔决策位，接受还是拒绝一目了然，调用方可以程序化处理；
- **`message`**——给人（或 LLM）看的理由；
- **`counter_proposal`**——拒绝时不是把门摔上，而是给出可接受的条件（"至少 7 天"）。发起方拿到还价后可以修改提案再来一轮，直到 `accepted: True` 或彻底放弃。

主流程验证了这个握手（第 77-82 行）：agent2 以 `deadline:5` 发起 → agent1 评估 `5 < 7` → 返回 `accepted: False` + 还价 `{"deadline": 7}`。虽然示例只走了一轮，但**"提案 → 评估 → 还价"的消息结构已经把多轮协商的轨道铺好了**——这正是多智能体系统里任务分配、资源竞价等高级协作模式的原型。

（顺带一提：这里解析提案又用了 `eval`，且包在裸 `except` 里返回"无效的提案格式"——教学代码的省事写法，生产中应换 `json.loads` + 明确的 schema 校验。）

## 🎯 剥完之后：它在本章的位置

A2A 应用篇回答的问题是：**协议通了之后，业务系统长什么样？**三个文件给出三个层次的答案：

| 模式 | 关键机制 | 适用场景 |
|---|---|---|
| 直连（Simple） | `A2ATool(agent_url=...)` 一行接入 | 固定的一对一委托 |
| 路由（CustomerService） | 工具 description + LLM 分诊 | 前台/后台专家架构 |
| 协商（Negotiation） | `accepted` / `counter_proposal` 消息结构 | 任务分配、条件谈判 |

但一个新问题浮出水面：客服系统里接待员**硬编码**了 6000、6001 两个 URL。专家扩到五十个、节点随时上下线时，"我该连谁"本身就成了难题——这就是下一篇 ANP（服务发现与组网）要接手的活。
