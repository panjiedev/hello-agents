# 天气智能体实战篇 剥洋葱式讲解

> 源文件：`code/chapter10/14_weather_mcp_server.py`（77 行）、`14_test_weather_server.py`（40 行）、`14_weather_agent.py`（58 行）
> 一句话概括：**用"服务端 → 测试脚本 → 智能体"三个文件走完一个 MCP 项目的标准开发流程：先把能力做成服务器，再用客户端验证，最后交给 LLM 对用户说人话。**

---

## 🧅 第一层（最外层）：这组文件在干什么？

前面几篇把 MCP 的客户端、服务端分开讲，这一篇把它们合成一个**可以直接跑的最小完整项目**：查天气。三个文件对应工程上的三个角色：

| 文件 | 角色 | 类比 |
|---|---|---|
| `14_weather_mcp_server.py` | 能力提供方（MCP 服务端） | 后端 |
| `14_test_weather_server.py` | 验证方（MCP 客户端） | 集成测试 |
| `14_weather_agent.py` | 用户界面（SimpleAgent + MCPTool） | 前端 |

值得先说破的一点：`14_weather_mcp_server.py` 与服务端篇讲过的 `weather-mcp-server/server.py` **业务代码完全相同**，唯一区别在最后一行——前者 `weather_server.run()` 走本地 stdio，后者 `run(transport="http", host, port)` 供云端发布。同一份能力，两种部署形态，这本身就是 MCP"协议与传输解耦"的最佳注脚。

## 🧅 第二层：`14_weather_mcp_server.py`——把真实世界包成三个工具

服务器骨架（第 12、70-76 行）：

```python
weather_server = MCPServer(name="weather-server", description="真实天气查询服务")

weather_server.add_tool(get_weather)
weather_server.add_tool(list_supported_cities)
weather_server.add_tool(get_server_info)

if __name__ == "__main__":
    weather_server.run()
```

三个工具的分工很有代表性：`get_weather` 是主业务，`list_supported_cities` 是能力边界查询（LLM 可以先问"你支持哪些城市"再决定怎么答复用户），`get_server_info` 是自我介绍——**一个体贴的 MCP 服务器不只提供功能，还提供"关于功能的信息"**。

真实数据来自免费天气源 wttr.in（第 22-40 行）：

```python
def get_weather_data(city: str) -> Dict[str, Any]:
    city_en = CITY_MAP.get(city, city)
    url = f"https://wttr.in/{city_en}?format=j1"
    response = requests.get(url, timeout=10)
    response.raise_for_status()
    data = response.json()
    current = data["current_condition"][0]
    return {
        "city": city,
        "temperature": float(current["temp_C"]),
        "feels_like": float(current["FeelsLikeC"]),
        "humidity": int(current["humidity"]),
        "condition": current["weatherDesc"][0]["value"],
        "wind_speed": round(float(current["windspeedKmph"]) / 3.6, 1),
        ...
    }
```

细节复盘（服务端篇讲过，这里是实战重现）：`CITY_MAP` 把"北京"翻成"Beijing"让用户说中文（第 14-19 行）；`timeout=10` 防外部 API 卡死；返回值不透传原始 JSON 而是重组成稳定字段，甚至顺手做了单位换算（`windspeedKmph / 3.6` 得到 m/s）。而对外的 `get_weather` 用 try/except 把任何异常都变成 `{"error": ..., "city": ...}` 的 JSON（第 44-50 行）——错误也是数据，LLM 读得懂。

## 🧅 第三层：`14_test_weather_server.py`——先当自己的第一个客户

服务器写完不要急着接 Agent，先用裸客户端验证协议链路（第 10-32 行）：

```python
server_script = os.path.join(os.path.dirname(__file__), "14_weather_mcp_server.py")
client = MCPClient(["python", server_script])

async with client:
    info = json.loads(await client.call_tool("get_server_info", {}))
    print(f"服务器: {info['name']} v{info['version']}")

    cities = json.loads(await client.call_tool("list_supported_cities", {}))
    print(f"支持城市: {cities['count']} 个")

    weather = json.loads(await client.call_tool("get_weather", {"city": "北京"}))
    if "error" not in weather:
        print(f"\n北京天气: {weather['temperature']}°C, {weather['condition']}")
```

四个测试由浅入深：服务器活着吗（info）→ 能力边界对吗（cities）→ 主流程通吗（北京）→ 再来一次稳吗（深圳）。两个工程细节：

- **`os.path.dirname(__file__)` 拼服务器路径**——不依赖运行时的工作目录，从任何位置执行脚本都能找到服务器文件；
- **`if "error" not in weather`**——因为服务器约定"错误也返回 JSON"，测试端检查的是 `error` 字段而不是捕异常，两端契约严丝合缝。

这一步的价值在于**隔离故障域**：如果这里就失败，问题在服务器或网络；如果这里通过而 Agent 表现异常，问题一定在提示词或工具装配。没有这个中间验证层，排查就是大海捞针。

## 🧅 第四层：`14_weather_agent.py`——给服务器配一张会聊天的嘴

最后一层把测试脚本里的手动调用换成 LLM 自动调用（第 11-28 行）：

```python
def create_weather_assistant():
    llm = HelloAgentsLLM()

    assistant = SimpleAgent(
        name="天气助手",
        llm=llm,
        system_prompt="""你是天气助手，可以查询城市天气。
使用 get_weather 工具查询天气，支持中文城市名。
"""
    )

    server_script = os.path.join(os.path.dirname(__file__), "14_weather_mcp_server.py")
    weather_tool = MCPTool(server_command=["python", server_script])
    assistant.add_tool(weather_tool)

    return assistant
```

system_prompt 只有两句话，却各有分工：第一句定人设，第二句给关键提示——工具叫 `get_weather`、**支持中文城市名**。后半句尤其重要：没有它，LLM 可能"自作聪明"地把"北京"翻译成"Beijing"再传参，而服务器的 CITY_MAP 本来就认中文，画蛇添足反而可能出错。**提示词要传达的不是工具的存在（框架会注入工具清单），而是工具的使用习惯。**

文件还提供了两种运行模式（第 52-57 行）：`python 14_weather_agent.py demo` 跑一次演示，不带参数进入 `input()` 循环的交互模式——`quit`/`exit` 退出，一个最小可用的命令行天气助手。

## 🧅 洋葱心：一问一答背后的完整链路（`14_weather_agent.py` 第 36-37 行）

```python
response = assistant.run("北京今天天气怎么样？")
print(f"回答: {response}\n")
```

就这两行，运行时发生的事横跨了本章所有概念：

1. `MCPTool` 按 `server_command` 把天气服务器拉成子进程，通过 stdio 完成 MCP 握手，`list_tools` 拿到三个工具的名字、描述、参数 schema；
2. SimpleAgent 把工具清单织进提示词，LLM 读到用户问题后决定调用 `get_weather`，并生成参数 `{"city": "北京"}`；
3. 调用沿 MCP 协议进入服务器进程 → 服务器请求 wttr.in → 清洗数据 → JSON 顺原路返回；
4. LLM 拿到 `{"temperature": 3.0, "condition": "Sunny", ...}` 这样的结构化数据，**翻译成一句人话**："北京今天晴，气温 3 度，体感……"。

用户看到的是一句自然语言回答；三层结构里每一层都只干自己的事——服务器不懂对话，LLM 不懂 HTTP，MCP 在中间做标准化的信使。**这就是通信协议章节想让你带走的系统观：智能不在某一层里，而在层与层的清晰分工里。**

## 🎯 剥完之后：它在本章的位置

天气实战篇是全章的"毕业设计"，把前面所有讲解落成一条可复制的开发流程：

| 步骤 | 文件 | 用到的前置知识 |
|---|---|---|
| 1. 写服务器 | `14_weather_mcp_server.py` | MCP 服务端篇（add_tool、错误即数据） |
| 2. 裸客户端测试 | `14_test_weather_server.py` | MCP 客户端篇（MCPClient、async with、call_tool） |
| 3. 接入智能体 | `14_weather_agent.py` | MCP 客户端篇（MCPTool 进 Agent）+ 提示词工程 |
| 4.（可选）发布上线 | `weather-mcp-server/` | 服务端篇（HTTP 传输 + Smithery 打包） |

以后想把任何能力（数据库、内部 API、爬虫）接给智能体，照这四步抄作业即可。而当你的"天气助手"需要和别人的"行程助手"协作时——回到 A2A 篇和 ANP 篇，那里有它们相遇的方式。
