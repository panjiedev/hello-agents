# HelloAgent_difyCase.yml 剥洋葱式讲解

> 源文件：`code/chapter5/HelloAgent_difyCase.yml`（5017 行）
> 一句话概括：**一个 Dify"超级智能个人助手"——问题分类器把用户输入分发到九条专家分支（日常问答 / 文案 / 生图 / 生视频 / 查数 / 数据分析 / 地图 / 菜谱 / 新闻），是"意图路由 + 多分支"架构的教科书样本。**

---

## 🧅 第一层（最外层）：这个文件在干什么？

文件开头的 `app:` 块（第 1-8 行）自报家门：

```yaml
app:
  mode: advanced-chat
  name: 超级智能个人助手
```

`workflow.features` 块（第 33-87 行）则暴露了它的"产品形态"：支持文件上传、语音输入（`speech_to_text`）、语音播报（`text_to_speech`），开场白是"这里是私人超级智能体"，并预置了七个建议问题——**这七个问题正好对应七条分支**，等于把整张图的功能清单印在了聊天窗口上：

```yaml
suggested_questions:
- 今天深圳的天气怎么样？        # → 高德MCP
- 今日ai新闻推荐                # → 新闻MCP
- 今日食谱推荐                  # → 吃什么MCP
- 帮我生成图片：玫瑰咖啡         # → Seedream 文生图
- 帮我生成视频：一个漂亮的...    # → Seedance 文生视频 + 轮询循环
- 帮我查数据：熊大几岁了？       # → text2SQL 查询链
- 帮我分析数据：学科分布情况     # → text2SQL + 可视化 Agent
```

主体是 `workflow.graph`：`edges`（第 89-438 行）+ `nodes`（第 439 行至文件尾，共 31 个节点）。

## 🧅 第二层：一颗路由器，九条分支

把 edges 里的 source→target 全部连起来，骨架是这样的：

```
开始 → 问题分类器 ─┬→ ① 日常助手(agent) ──────────────→ 直接回复
                   ├→ ② 优化文案助手(llm) ─────────────→ 直接回复
                   ├→ ③ Seedream-文生图(tool) ─────────→ 直接回复
                   ├→ ④ Seedance-文生视频(tool) → 循环[轮询] → 直接回复
                   ├→ ⑤ text2data → excute_sql → 数据整理(llm) → 直接回复
                   ├→ ⑥ text2data(1) → excute_sql(1) → 数据可视化分析(agent) → 直接回复
                   ├→ ⑦ 高德MCP(agent) ───────────────→ 直接回复
                   ├→ ⑧ 吃什么MCP(agent) ─────────────→ 直接回复
                   └→ ⑨ 新闻MCP(agent) ───────────────→ 直接回复
```

`问题分类器` 节点（第 459-508 行，type: `question-classifier`）就是那颗路由器。它的配置出奇地少——一个模型（deepseek-chat）加九行分类文本：

```yaml
classes:
- { id: '1',  name: 一般性日常生活问题 }
- { id: '2',  name: 优化文案 }
- { name: 生成图片 }
- { name: 生成视频 }
- { name: 查询数据 }
- { name: 数据分析 }
- { name: 城市的天气、地图经纬度、IP地址、骑行路径规划、驾车路径规划、... }
- { name: 查询全部菜谱、今天可以吃什么好吃的、智能推荐一周菜谱、... }
- { name: 今天有什么最新新闻、行业动态追踪 }
```

注意后三条的写法：不是抽象的类别名，而是**把用户可能的问法穷举出来当类名**——类名本身就是 few-shot 示例。这颗"路由器"里没有任何 if-else，分类完全靠 LLM 语义理解。

每条分支的终点都是一个 `answer` 节点（直接回复），内容只有一行变量引用，如 `{{#1753154086254.text#}}`（第 958 行，引用优化文案节点的输出）、`{{#1779006596264.files#}}`（第 977 行，引用文生图节点产出的**文件**）。`{{#节点id.字段#}}` 就是 Dify 的数据流语法。

## 🧅 第三层：三种"会思考的节点"——llm、agent、agent+MCP

九条分支里藏着三个梯度的智能：

**梯度一：`llm` 节点（纯提示词，无工具）。** 如 `优化文案助手`（第 876-944 行），一段五段式系统提示词（角色人设/背景/任务目标/限制提示/输出格式要求）+ 用户消息 `{{#sys.query#}}`，进来一段文案、出去一段更好的文案。本章所有提示词都遵循这个五段模板——这是低代码平台上的"提示词工程规范化"。

**梯度二：`agent` 节点（FunctionCalling 策略）。** 如 `日常助手`（第 509 行起，`agent_strategy_name: function_calling`，第 831 行），比 llm 节点多了 `tools` 字段——挂了一个内置 `time` 工具（第 540-548 行），模型自己决定要不要查当前时间。`数据可视化分析`（第 996-1100 行）同理，挂的是三个图表工具，且提示词里把工具名直接写给模型看：

```
可调用工具："generate_pie_chart" | "generate_column_chart" | "generate_line_chart"
```

有趣的细节：这个节点用的是 `gpt-4o`（第 1053 行）——同一张图里不同节点可以用不同厂商的模型，**按任务挑模型**是工作流平台的隐藏福利。

**梯度三：`agent` 节点（ReAct + MCP 策略）。** 高德/吃什么/新闻三个 MCP 节点（第 1893-1894 行，`agent_strategy_label: ReAct (Support MCP Tools)`）。以 `高德MCP` 为例（第 1803-1905 行），核心配置就两行：

```yaml
instruction: 根据用户输入{{#sys.query#}}，使用amap-maps实现查询
mcp_servers_config: '{ "amap-maps": { "url": "https://mcp.api-inference.modelscope.net/.../sse" } }'
```

**接入一整套高德地图能力（天气/路径规划/周边搜索），只需要一个 MCP Server 的 URL**——工具列表是运行时从服务器动态拉取的。这三个节点的模型选了 `deepseek-reasoner`（第 1817 行），因为 ReAct 循环吃推理能力。

## 🧅 第四层：两条 SQL 流水线——工具节点的"确定性接力"（第 2250-3100 行）

"查询数据"和"数据分析"两条分支的前半段完全一样，是两个 `tool` 节点的接力：

1. `rookie_text2data`（第 2678-2756 行）：text2SQL 插件。配置里写死了 MySQL 连接信息（host/端口/账号），`custom_prompt` 里贴了表结构 `CREATE TABLE test01 (name, age, sex)`，用 `deepseek-coder`、**temperature 0**（第 2696 行）把 `{{#sys.query#}}` 翻译成 SQL——又是"输出要被机器消费，就把随机性拧到零"；
2. `rookie_excute_sql`：拿上一步的 SQL 去真实数据库执行，返回结果文本。

之后两条分支分道扬镳："查询数据"接一个 `数据整理` llm 节点（第 2263-2273 行）把裸数据说成人话（user 消息同时引用了 SQL 结果和原始问题：`数据：{{#1760526609582.text#}}` + `用户问题：{{#sys.query#}}`）；"数据分析"则交给梯度二的可视化 Agent 画图。

**同样的数据，不同的下游，就是不同的产品功能**——这是工作流"节点复用"的直观例子。

## 🧅 洋葱心：文生视频分支的轮询循环（第 3339-3654 行）

九条分支里唯一的控制流难点。文生视频是**异步任务**：提交后拿到的不是视频，是一个 `task_id`，要反复查询直到生成完毕。Dify 用一个 `loop` 节点（第 3339-3352 行，`loop_count: 20` 封顶）解决：

```
Seedance-文生视频 ──→ ┌────────────── 循环体 ──────────────┐
                      │ 参数提取器2 → Seedance-视频结果查询   │
                      │        ↓                             │
                      │   条件分支: files 为空?               │
                      │     是 → 等待10秒 → (下一轮)          │
                      │     否 → 直接回复(视频文件) → 退出循环 │
                      └──────────────────────────────────────┘
```

四个零件各司其职：

- `参数提取器 2`（第 3387-3409 行，type: `parameter-extractor`）：用 LLM 从上游文本里抽出结构化的 `task_id`——**"从自然语言里抠字段"本身也是一个 LLM 任务**，Dify 把它做成了专用节点；
- `条件分支`（第 3534-3552 行）：判据是 `1779007244895.files` 这个 `array[file]` 是否为 `empty`——文件数组还空着，说明视频没生成完；
- `等待`（第 3620-3638 行）：一个叫 `agimaster/justwait` 的社区插件，`tool_description` 写得很直白："等待指定的秒数，类似于Python的time.sleep()函数"，写死 10 秒；
- `退出循环`（loop-end，第 3568-3574 行）。

手写代码里三行 `while + sleep + break`，在画布上变成了一个循环容器加四个节点——**低代码在"顺序编排"上很省事，在"控制流"上反而更啰嗦**，这是选型时值得记住的权衡。

## 🎯 剥完之后：它在本章的位置

Dify 案例回答的问题是：**当一个助手要会九种本领时，图该怎么画？**答案是"先分类，再分发，一支一专家"：

| 对比维度 | Dify 本例 | 其他三例 |
|---|---|---|
| 路由 | 问题分类器（9 类，类名即示例） | Coze 无路由；n8n 无路由；FastGPT 同样用分类节点（4 类） |
| 智能梯度 | llm → agent(FC) → agent(ReAct+MCP) 三档并存 | FastGPT 也是 chatNode/tools 双档；n8n 单档 |
| 模型策略 | 按节点混用 deepseek-chat / deepseek-reasoner / deepseek-coder / gpt-4o | FastGPT 混用 glm/doubao/deepseek，思路相同 |
| 控制流 | 循环 + 条件分支 + 等待（异步轮询） | 其余三例均无循环 |
| 数据引用 | `{{#节点id.字段#}}` / `{{#sys.query#}}` | Coze 用 `ref_node`，FastGPT 用 `{{$节点id.字段$}}` |

它与 FastGPT 案例是一对镜像：Dify 的九条分支**彼此独立、各自到达终点**；FastGPT 的分支内部还要**多位专家串行接力**。看完这篇，去 FastGPT 篇看"分支之内如何流水线"。
