# test_*.py 六个测试文件总览（剥洋葱式讲解）

> 源文件：`code/chapter7/test_simple_agent.py`、`test_react_agent.py`、`test_my_calculator.py`、`test_advanced_search.py`、`test_plan_solve_agent.py`、`test_reflection_agent.py`
> 一句话概括：**六个可直接运行的脚本，每个点亮框架的一种用法——合起来就是 HelloAgents 框架的"活文档"。**

---

## 🧅 第一层（最外层）：这些文件在干什么？

它们不是 pytest 意义上的单元测试（没有断言、没有 fixture），而是**演示脚本**：每个文件搭一个最小场景，把本章某个自定义组件跑给你看。共同的开场白只有三行：

```python
from dotenv import load_dotenv
load_dotenv()
llm = HelloAgentsLLM()
```

零参数构造 `HelloAgentsLLM()`——配置全部从 `.env` 来（参见 `.env.example` 的四个 `LLM_*` 变量），框架自动检测 provider。第四章需要讲半篇的"配置瀑布"，在使用侧已经浓缩成一行。

六个脚本各自展示什么，一表看清：

| 测试文件 | 被测对象 | 展示的框架用法 |
|---|---|---|
| `test_simple_agent.py` | `MySimpleAgent` | 无工具对话 / 带工具对话 / 流式 / 动态工具管理 / 历史查询 |
| `test_react_agent.py` | `MyReActAgent` | `register_function` 注册工具、多题型推理、`custom_prompt` 注入 |
| `test_my_calculator.py` | `my_calculator_tool` | 工具的独立单测 + "工具结果喂给 LLM 组织答案"的手动流水线 |
| `test_advanced_search.py` | `my_advanced_search` | 多源搜索、无 API key 时的降级提示、`get_tools_description` |
| `test_plan_solve_agent.py` | `MyPlanAndSolveAgent`（见下文注意） | 规划-执行范式的框架化用法 |
| `test_reflection_agent.py` | `MyReflectionAgent`（见下文注意） | 用 `custom_prompts` 字典把同一 Agent 变身不同专家 |

> ⚠️ **注意**：`test_plan_solve_agent.py` 导入的 `my_plan_solve_agent.py` 和 `test_reflection_agent.py` 导入的 `my_reflection_agent.py` **并不在本目录中**——这两个 Agent 的实现留给读者按书中章节内容自行完成（可参照 `my_react_agent.py` 的继承套路），测试脚本先行给出了"验收标准"。

## 🧅 第二层：`test_simple_agent.py`——一个 Agent 的四段进化

这是覆盖面最广的脚本，四个测试恰好是 `MySimpleAgent` 能力的递进解锁：

1. **测试1 基础对话**：只传 `name` / `llm` / `system_prompt`，不给工具——验证"退化优雅"，没工具时它就是个普通聊天机器人；
2. **测试2 工具增强**：`ToolRegistry()` + `register_tool(CalculatorTool())`（注意：这里用的是**框架内置**的 `CalculatorTool`，不是我们自写的那个），问 `15 * 8 + 32`，触发 `[TOOL_CALL:...]` 协议全流程；
3. **测试3 流式响应**：`for chunk in basic_agent.stream_run(...): pass`——和 `my_main.py` 同款的"喝干生成器"写法，内容已在方法内部实时打印；
4. **测试4 动态工具管理**：`has_tools()` 从 `False` 到 `True`，现场验证 `add_tool` 会自动创建注册表的贴心设计。

最后一行 `len(basic_agent.get_history())` 顺手展示了继承自基类的历史记录——四个测试的对话全被记着账。

## 🧅 第三层：`test_react_agent.py`——三种题型 + 换脑实验

前半段 `test_react_agent()` 用三类问题给 `MyReActAgent` 做梯度体检：

- **纯计算**（`(25 + 15) * 3 - 8`）→ 应一步调 `calculate` 工具后 Finish；
- **纯检索**（Python 发布年份）→ 应调 `search` 工具；
- **复合推理**（30 人班级 60% 女生，男生几人）→ 考验多步循环：先算女生、再算男生。

注册工具时的 `try: from hello_agents import calculate ... except ImportError` 写法值得注意——工具缺席不会让测试崩溃，只是跳过注册，与 `my_advanced_search.py` 的探测思想一脉相承。

后半段 `test_custom_prompt()` 是本文件的点睛：把一份精简的"数学专家版"提示词通过 `custom_prompt` 参数注进去，同一个 Agent 类立刻换了话风——**验证了"提示词即配置"这一设计承诺真的兑现了**。

## 🧅 第四层：两个工具测试——先单测，再合体

`test_my_calculator.py` 分两步：

1. `test_calculator_tool()` 用五个表达式（四则 + `sqrt(16)`）直接打 `registry.execute_tool("my_calculator", ...)`——**不经过 LLM 的工具裸测**，工具有问题在这一层就暴露；
2. `test_with_simple_agent()` 手动摆了一条"工具先算、LLM 后说"的流水线：先 `execute_tool` 拿到数字，再把结果塞进提示词让 `llm.think` 组织成自然语言。这其实是把 Agent 循环**手动展开了一步**——看懂这段，就看懂了所有 Agent 框架在自动化什么。

`test_advanced_search.py` 同样三段式：批量查询实测、**无 API key 场景**（`test_api_configuration`，验证那段"配置指南"返回值）、以及 `get_tools_description()` 输出——让你亲眼看到注册时写的 `description` 最终长什么样、LLM 会读到什么。

## 🧅 洋葱心：所有测试共用的一个句式

六个文件千姿百态，但核心动作全是同一个句式的变奏：

```python
组件 = My某某(name=..., llm=llm, ...)   # 继承框架基类的自定义组件
结果 = 组件.run(问题)                    # 统一的 run 入口
```

`MySimpleAgent.run`、`MyReActAgent.run`、`MyPlanAndSolveAgent.run`、`MyReflectionAgent.run`——**不同范式、同一接口**。这正是框架 `Agent` 基类用抽象方法 `run` 立下的契约：范式内部再复杂，对使用者永远只是一次 `run(input_text)`。第四章三种范式各有各的调用方式；本章它们被统一在一个签名之下，这就是框架化最直观的红利。

## 🎯 剥完之后：它们在本章的位置

测试脚本是本章的"第七个老师"：正向文档教你怎么写组件，测试脚本教你**组件写好后别人怎么用**。读代码时推荐的动线是——先读组件源码（`my_*.py`），再打开对应测试跑一遍，让日志里的 emoji（🤖 / 🔧 / ✅）把静态代码变成动态叙事。而那两个"缺席"的被测文件（`my_plan_solve_agent.py`、`my_reflection_agent.py`），正好是留给你的结业作业：拿着现成的测试当验收标准，用 `my_react_agent.py` 的继承套路，把第四章的 Plan-and-Solve 和 Reflection 也框架化一遍。
