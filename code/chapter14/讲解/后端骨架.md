> 一句话概括：**四个文件搭出 DeepResearch 的"房子"——HTTP 门面、配置中枢、状态数据结构、文本工具箱——智能体本体（agent.py）只需拎包入住。**

---

## 🧅 第一层（最外层）：这四个文件在干什么？

前面各章的智能体都是"脚本"：`python xxx.py` 跑一次就结束。本章是**综合项目**，智能体要作为一个长期运行的服务，被浏览器里的前端反复调用。于是需要一套工程骨架：

| 文件 | 角色 | 一句话 |
|---|---|---|
| `main.py` | HTTP 门面 | 用 FastAPI 把智能体暴露成 `/research` 和 `/research/stream` 两个接口 |
| `config.py` | 配置中枢 | 一个 Pydantic 模型收拢全部可调参数，从环境变量装配 |
| `models.py` | 状态数据结构 | `TodoItem` + `SummaryState`，整个研究流程的"记忆载体" |
| `utils.py` | 文本工具箱 | 去 `<think>`、去重格式化搜索结果、生成来源清单 |

它们共同的特点是：**不含任何"智能"**。智能全在 `agent.py` 和提示词里，骨架只负责把请求接进来、把配置传下去、把状态存起来、把文本理干净。

## 🧅 第二层：main.py——一个智能体，两种出口

`main.py` 的核心是 `create_app()` 里注册的两个 POST 接口，它们调用的是**同一个** `DeepResearchAgent`，区别只在返回方式：

**出口一：一次性返回（第 118-147 行）**

```python
@app.post("/research", response_model=ResearchResponse)
def run_research(payload: ResearchRequest) -> ResearchResponse:
    config = _build_config(payload)
    agent = DeepResearchAgent(config=config)
    result = agent.run(payload.topic)
```

调用 `agent.run()`，阻塞到整个研究做完，把最终报告和任务列表打包成 JSON 一次性返回。适合脚本调用，但一次深度研究要几分钟，浏览器等不起。

**出口二：SSE 流式返回（第 149-173 行）**

```python
def event_iterator() -> Iterator[str]:
    for event in agent.run_stream(payload.topic):
        yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"

return StreamingResponse(
    event_iterator(),
    media_type="text/event-stream",
    ...
)
```

调用 `agent.run_stream()`——它是一个**生成器**，研究过程中每发生一件事（规划完成、搜到来源、总结生成一段、工具被调用……）就 `yield` 一个事件字典。`main.py` 把每个字典序列化成 `data: {...}\n\n` 的 SSE（Server-Sent Events）格式推给浏览器。前端章会看到，正是这条事件流驱动了整个 UI 的实时刷新。

注意 `event_iterator` 里的 try/except（第 161-164 行）：流式响应的 HTTP 状态码在第一个字节发出后就定死了，中途出错**没法再改成 500**，所以错误也被包装成一个 `{"type": "error"}` 事件顺着流发出去——错误处理协议从"HTTP 状态码"降级到了"事件类型"，这是所有流式接口的通用套路。

另外两个小角色：`/healthz` 健康检查；`startup` 钩子把配置打进日志、并用 `_mask_secret`（第 58-66 行）只露 API Key 首尾 4 个字符——把密钥打进日志是安全事故，这个小函数是标准防御。

## 🧅 第三层：config.py——一张 Pydantic 表单收拢所有旋钮

`Configuration`（第 16-88 行）用 Pydantic `Field` 声明了十几个可调参数：研究轮数上限、LLM 提供商（ollama / lmstudio / 自定义 OpenAI 兼容服务）、搜索后端（枚举 `SearchAPI`：tavily / duckduckgo / perplexity / searxng / advanced）、是否启用笔记、笔记目录、是否抓全文、是否剥 `<think>`……

装配逻辑在 `from_env`（第 90-129 行），是一条三级瀑布：

```python
# 1. 字段名大写直接映射环境变量
for field_name in cls.model_fields.keys():
    env_key = field_name.upper()
    if env_key in os.environ:
        raw_values[field_name] = os.environ[env_key]
# 2. 显式别名表兜底（setdefault，不覆盖）
for key, value in env_aliases.items():
    if value is not None:
        raw_values.setdefault(key, value)
# 3. 请求级 overrides 最高优先
if overrides:
    for key, value in overrides.items():
        if value is not None:
            raw_values[key] = value
```

优先级是 **HTTP 请求参数 > 环境变量 > Field 默认值**。回看 `main.py` 的 `_build_config`：前端下拉框选的搜索引擎就是通过 `overrides={"search_api": ...}` 传进来的——用户不用改服务器配置，就能在每次请求时切换搜索后端。

还有个小而关键的方法 `sanitized_ollama_url`（第 131-137 行）：Ollama 原生地址不带 `/v1`，而 OpenAI 客户端需要 `/v1` 后缀，这里自动补齐——消化掉一个新手极易踩的坑。

## 🧅 第四层：models.py——研究流程的"记忆载体"

只有两个主角：

```python
@dataclass(kw_only=True)
class TodoItem:
    id: int
    title: str        # 任务名
    intent: str       # 任务要解决的问题
    query: str        # 检索关键词
    status: str = "pending"   # pending → in_progress → completed / skipped
    summary: Optional[str]         # 执行完的总结
    sources_summary: Optional[str] # 来源清单
    note_id: Optional[str]         # 关联的笔记 ID
    ...
```

`TodoItem` 就是一条待办任务，它自带一个**微型状态机**：`status` 从 `pending` 出发，进行中变 `in_progress`，搜不到结果变 `skipped`，成功变 `completed`。前端任务清单上的彩色标签，对应的正是这四个状态。

```python
@dataclass(kw_only=True)
class SummaryState:
    research_topic: str
    web_research_results: Annotated[list, operator.add]
    sources_gathered: Annotated[list, operator.add]
    research_loop_count: int = 0
    todo_items: Annotated[list, operator.add]
    structured_report: Optional[str]
    ...
```

`SummaryState` 是**一次研究的全部状态**：主题、所有任务、搜到的原始材料、来源、最终报告。整个后端就是一台围绕它运转的机器——planner 往里写 `todo_items`，每个任务执行时往 `web_research_results` 里追加材料，reporter 最后读全量状态写出 `structured_report`。

`Annotated[list, operator.add]` 这个写法值得一提：它是 LangGraph 风格的"状态合并注解"（列表用加法合并），本项目虽然自己写了编排、没用 LangGraph，但保留了这个注解，暗示了它的血统——它脱胎于 LangGraph 官方的 local-deep-researcher 项目。

## 🧅 洋葱心：utils.py 的 `strip_thinking_tokens`（第 19-26 行）

```python
def strip_thinking_tokens(text: str) -> str:
    while "<think>" in text and "</think>" in text:
        start = text.find("<think>")
        end = text.find("</think>") + len("</think>")
        text = text[:start] + text[end:]
    return text
```

短短六行，却是本地模型时代的必备补丁：DeepSeek-R1、QwQ 这类推理模型会先输出一段 `<think>...</think>` 的思考过程再给答案。思考过程混进任务总结或最终报告里，用户看到的就是一堆自言自语。这个 while 循环把所有闭合的 think 段掐掉，只留干货。全后端有三处调用它（planner 解析前、summarizer 输出后、reporter 输出后），下一篇服务层还会看到它的**流式版本**——在 chunk 尚未凑齐 `</think>` 时如何边收边剥。

`utils.py` 的另一半是搜索结果的两种"摆盘"：

- `deduplicate_and_format_sources`（第 29-70 行）：按 URL 去重，拼成"信息来源 / URL / 信息内容 / 详细内容"的长文本，**喂给 LLM 做总结用**；全文按 `max_tokens_per_source * 4` 字符截断（`CHARS_PER_TOKEN = 4` 是"一个 token 约四个字符"的粗估），防止把上下文窗口撑爆。
- `format_sources`（第 73-84 行）：拼成 `* 标题 : URL` 的短清单，**给人看、给前端渲染引用列表用**。

同一份搜索结果，机器吃全文、人看清单——两个函数就是这一句话。

## 🎯 剥完之后：它在本章的位置

一次请求的完整旅程，骨架四件套各站一岗：

```
浏览器 POST /research/stream
  → main.py 接请求、_build_config 用 config.py 装配 Configuration
  → new DeepResearchAgent(config)          ← 下一篇的主角
  → agent.run_stream() 围着 SummaryState / TodoItem（models.py）转
  → 过程中用 utils.py 清洗文本、格式化搜索结果
  → 每个事件被 main.py 包成 SSE 推回浏览器
```

骨架把"工程"与"智能"切开了：换 Web 框架只动 `main.py`，换模型供应商只改环境变量，改研究流程的数据结构只碰 `models.py`。接下来剥 `agent.py`——住进这间房子的主人。
