# frontend/src（App.vue + services/api.ts）剥洋葱式讲解

> 源文件：
> - `code/chapter14/helloagents-deepresearch/frontend/src/services/api.ts`（96 行）
> - `code/chapter14/helloagents-deepresearch/frontend/src/App.vue`（2304 行，其中脚本约 650 行，其余是模板与样式）
>
> 一句话概括：**前端是后端事件流的"投影仪"——api.ts 负责把 SSE 字节流切成一个个 JSON 事件，App.vue 用一张事件分发表把每类事件翻译成对应的 UI 更新：任务卡片、打字机总结、来源列表、工具调用记录、最终报告。**

---

## 🧅 第一层（最外层）：这两个文件在干什么？

后端 `run_stream` 吐出的是一串事件：`todo_list`、`task_status`、`sources`、`task_summary_chunk`、`tool_call`、`final_report`……前端的全部工作就是**让这串事件"长"成界面**：

- `api.ts`：唯一的网络层。POST `/research/stream`，逐字节读响应体，还原出一个个事件对象，逐个回调给上层。
- `App.vue`：唯一的页面组件。维护一组响应式状态（任务列表、日志、报告），`handleSubmit` 里那个 300 行的事件处理器是全前端的心脏。

值得注意的是它**没有**用 WebSocket，也没用浏览器原生 `EventSource`——因为 `EventSource` 只支持 GET，而研究请求要 POST 一个 JSON body，所以这里用 `fetch` + `ReadableStream` 手工实现了 SSE 客户端。

## 🧅 第二层：api.ts——手搓一个 SSE 解析器（第 18-96 行）

```typescript
const reader = body.getReader();
const decoder = new TextDecoder("utf-8");
let buffer = "";

while (true) {
  const { value, done } = await reader.read();
  buffer += decoder.decode(value || new Uint8Array(), { stream: !done });

  let boundary = buffer.indexOf("\n\n");
  while (boundary !== -1) {
    const rawEvent = buffer.slice(0, boundary).trim();
    buffer = buffer.slice(boundary + 2);
    if (rawEvent.startsWith("data:")) {
      const event = JSON.parse(rawEvent.slice(5).trim()) as ResearchStreamEvent;
      onEvent(event);
      if (event.type === "error" || event.type === "done") return;
    }
    boundary = buffer.indexOf("\n\n");
  }
  if (done) break;
}
```

三个要点：

1. **`\n\n` 是事件边界**。回看后端 `main.py`：`yield f"data: {json.dumps(event)}\n\n"`——空行分隔是 SSE 协议的规定。网络传输会把事件任意切碎或粘连（半个 JSON、两个事件挤在一个 chunk），所以必须攒 `buffer`，只在看到完整的 `\n\n` 时才切一刀。这和上一篇 summarizer 里"等 `</think>` 凑齐再发射"是同一个思想：**流式解析永远要为'边界还没到'留一手**。
2. **`decoder.decode(value, { stream: !done })`**：UTF-8 的一个汉字占 3 字节，chunk 可能正好切在半个汉字上；`stream: true` 让解码器把不完整的字节序列留到下一轮，避免乱码。中文项目里漏了这个参数，界面就会随机蹦"�"。
3. **`event.type === "done"` 主动收工**，加上 `options.signal` 透传 `AbortSignal`——上层可以随时按"取消研究"掐断连接。

这个函数的签名很有代表性：`runResearchStream(payload, onEvent, options)`——**网络层不懂任何业务，只把事件原样上交**；懂业务的是下一层的分发表。

## 🧅 第三层：App.vue 的状态设计——`TodoTaskView` 是 TodoItem 的前端镜像（第 364-397 行）

```typescript
interface TodoTaskView {
  id: number; title: string; intent: string; query: string;
  status: string;                 // pending / in_progress / completed / skipped
  summary: string;                // 由 task_summary_chunk 逐段拼出来
  sourceItems: SourceItem[];      // 解析后的来源（标题+URL+摘要）
  notices: string[];              // 系统提示（如"搜索后端已降级"）
  noteId: string | null;          // 笔记徽章
  toolCalls: ToolCallLog[];       // 工具调用记录
}

const todoTasks = ref<TodoTaskView[]>([]);
const activeTaskId = ref<number | null>(null);
const reportMarkdown = ref("");
const progressLogs = ref<string[]>([]);
```

对照后端 `models.py` 的 `TodoItem`，字段几乎一一对应——**后端的状态机，在前端有一个响应式副本**。副本怎么和本尊保持同步？不靠轮询，全靠事件驱动。`findTask(taskId)`（第 646-657 行）就是同步的地址簿：每个事件带着 `task_id`，前端按 id 找到对应卡片再更新——上一篇说的"并发在后端、分拣在前端"，分拣动作就发生在这。

另有一个小巧思 `pulse`（第 443-451 行）：某块内容更新时给它加 1.2 秒的高亮动画（`block-highlight`），用视觉闪烁告诉用户"这里刚变过"——流式 UI 的体验细节。

## 🧅 第四层：事件分发表——每类事件一段 UI 剧本（第 696-940 行）

`handleSubmit` 把一个巨型回调传给 `runResearchStream`，本质是一张 `event.type → 处理逻辑` 的分发表。逐类过一遍，正好把后端事件剧本的"观众视角"补齐：

| 事件 | 前端反应 | 行号 |
|---|---|---|
| `status` | 追加进度日志时间轴；若带 task_id 还写进该任务的"系统提示" | 699-713 |
| `todo_list` | **一次性建出全部任务卡片**（防御性解析每个字段，缺啥补默认值），选中第一个任务 | 715-772 |
| `task_status` | 状态机翻牌：`in_progress` 清空旧内容并自动切换到该任务；`completed` 落定总结与来源并触发高亮；`skipped` 记一笔 | 774-816 |
| `sources` | 更新来源清单，`parseSources` 把后端的文本格式解析成结构化链接列表 | 818-852 |
| `task_summary_chunk` | **打字机核心**：`task.summary += chunk`，Vue 响应式让文字逐段长出来 | 854-868 |
| `tool_call` | 往该任务的"工具调用记录"面板追加一条（Agent → 工具、参数、结果、笔记 ID/路径） | 870-919 |
| `final_report` | 填充最终报告块并高亮 | 921-930 |
| `error` | 显示错误条，停止流程 | 932-939 |

最能体现"事件驱动 UI"的是两行代码的对比。后端并发跑 N 个任务时，用户此刻看的是任务 2，而任务 3 的 chunk 也在源源到达——

```typescript
task.summary += chunk;                        // 数据：不管在不在看，先记上
if (activeTaskId.value === task.id) {
  pulse(summaryHighlight);                     // 视觉：只有正被看的才闪
}
```

**数据更新与视觉反馈解耦**：每个任务的内容在后台各自生长，用户切换卡片时看到的永远是最新全量。

`parseSources`（第 453-568 行）值得多看一眼：它是一个逐行状态机，兼容后端 `format_sources` 的 `* 标题 : URL` 格式和 `deduplicate_and_format_sources` 的"信息来源:/URL:/信息内容:"格式（甚至中英文标签都兼容）——后端 utils.py 定义的文本格式，在这里被前端逆向解析回结构。**同一份协议，后端序列化、前端反序列化，两头的代码隔着 HTTP 遥相呼应。**

## 🧅 洋葱心：AbortController——给一条长流装上刹车（第 671-991 行）

```typescript
let currentController: AbortController | null = null;

const handleSubmit = async () => {
  if (currentController) currentController.abort();   // 新研究开始前，掐掉旧的
  const controller = new AbortController();
  currentController = controller;
  try {
    await runResearchStream(payload, onEvent, { signal: controller.signal });
  } catch (err) {
    if (err instanceof DOMException && err.name === "AbortError") {
      progressLogs.value.push("已取消当前研究任务");   // 取消不是错误
    } else {
      error.value = err instanceof Error ? err.message : "请求失败";
    }
  } finally {
    loading.value = false;
    if (currentController === controller) currentController = null;
  }
};

onBeforeUnmount(() => { currentController?.abort(); });
```

一次深度研究要跑几分钟，这条 fetch 连接就吊着几分钟。用户点"取消研究"、开启新研究、或直接关页面，都必须能立刻掐断它，否则旧流的事件会继续污染新界面。三处细节：

1. `abort()` 抛出的 `AbortError` 被**单独识别**——用户主动取消是正常操作，不该弹红色错误条；
2. `finally` 里 `if (currentController === controller)`——防止"旧请求的收尾把新请求的控制器置空"的竞态；
3. `onBeforeUnmount` 兜底，组件销毁时释放连接。

**长连接的生命周期管理，是流式前端和普通表单页最大的分野**——这十几行就是全部答案。

## 🎯 剥完之后：它在本章的位置

把前后端拼成完整闭环，一次深度研究的全景图：

```
用户输入主题 ── POST /research/stream ──→ main.py
                                            │ agent.run_stream()
  todo_list ──→ 任务卡片列表               │  ├ planner 拆题
  task_status ─→ 状态标签翻牌 + 进度条     │  ├ N 线程并发: search → summarizer
  sources ────→ 引用链接列表               │  │      （写笔记，tool_events 记账）
  task_summary_chunk → 打字机总结          │  ├ reporter 汇总（读笔记）
  tool_call ──→ 工具调用面板               │  └ 报告落盘为 conclusion 笔记
  final_report → 最终报告块                │
  done ───────→ 状态芯片变"研究流程完成"   ▼
        ←────────── SSE 事件流 ──────────  浏览器
```

前端没有一行"研究逻辑"，后端没有一行"界面逻辑"，两者之间只有一份**事件协议**（type + 字段约定）。这和贯穿全书的那条铁律是同一件事在更大尺度上的重演：小到一次 LLM 调用（提示词定协议、解析器兑现），大到一个全栈系统（后端定事件、前端渲染）——**先定协议，再各自实现，是智能体工程从函数到系统通用的组织术**。
