## 🧅 第一层（最外层）：这五个文件在干什么？

规划专家拆了题，总结专家读了料，报告专家要收尾——三位专家各自是独立的 LLM 会话，互相看不见对方的对话历史。他们靠什么协作？**笔记（NoteTool）**：磁盘上 `./notes/` 目录里的一个个 Markdown 文件，充当跨 Agent 的**中间记忆 / 共享黑板**。

| 文件 | 角色 |
|---|---|
| `notes.py` | 给总结专家生成"怎么记笔记"的操作指引文本 |
| `summarizer.py` | 总结专家的经纪人：拼提示词、跑总结、流式剥 `<think>` |
| `reporter.py` | 报告专家的经纪人：汇总所有任务 + 笔记索引，产出最终报告 |
| `text_processing.py` | 一个正则：从用户可见文本里抹掉 `[TOOL_CALL:...]` |
| `tool_events.py` | 书记员：记录每次工具调用，推断归属任务，转成前端事件 |

## 🧅 第二层：notes.py——把"笔记规范"翻译成提示词（第 10-58 行）

`build_note_guidance(task)` 只干一件事：根据任务**有没有笔记 ID**，生成两种操作指引。

任务已有笔记（规划阶段建过）：

```python
return (
    "笔记协作指引：\n"
    f"- 当前任务笔记 ID：{task.note_id}。\n"
    f"- 在书写总结前必须调用：[TOOL_CALL:note:{read_payload}] 获取最新内容。\n"
    f"- 完成分析后调用：[TOOL_CALL:note:{update_payload}] 同步增量信息。\n"
    ...
)
```

任务还没笔记：先教它 create，"创建成功后记录返回的 note_id，并在后续所有更新中复用"。

注意指引里的 `read_payload` / `update_payload` 不是手写字符串，而是 `json.dumps(...)` 生成的——**教模型调用工具的示例，本身就用真代码序列化**，保证示例永远是合法 JSON，模型照抄不会错。`tags` 固定含 `deep_research` 和 `task_{id}`，这是后面 tool_events 反推任务归属的钩子。

先读后写（read-before-write）的要求也不是仪式：总结专家每个任务一个新实例、没有记忆，读笔记是它了解"规划专家当初怎么定义这个任务"的唯一途径。

## 🧅 第三层：summarizer.py——流式输出中实时剥 `<think>`（第 47-112 行）

同步版 `summarize_task` 平平无奇：拼提示词（主题 + 任务名 + 意图 + 检索上下文 + 笔记指引）→ `agent.run` → 事后 `strip_thinking_tokens` + `strip_tool_calls`。

真正的技术难点在流式版 `stream_task_summary`。问题：chunk 是一片一片来的，`<think>` 和 `</think>` 可能分属不同 chunk，甚至 `</think>` 还没到——**事后清洗的函数在流式场景下失效了**，必须边收边剥。解法是一个带游标的缓冲区：

```python
raw_buffer = ""      # 收到的全部原文
emit_index = 0       # 已经对外发射到哪个位置

def flush_visible() -> Iterator[str]:
    nonlocal emit_index, raw_buffer
    while True:
        start = raw_buffer.find("<think>", emit_index)
        if start == -1:
            # 后面没有 think 了，把剩余的全部发射
            segment = raw_buffer[emit_index:]; emit_index = len(raw_buffer)
            if segment: yield segment
            break
        if start > emit_index:
            # think 之前的部分是安全的，先发射
            yield raw_buffer[emit_index:start]; emit_index = start
        end = raw_buffer.find("</think>", start)
        if end == -1:
            break            # ← 闭合标签还没到，按兵不动，等下一个 chunk
        emit_index = end + len("</think>")   # 跳过整个 think 段
```

洋葱心就在那句 `if end == -1: break`：看到 `<think>` 开头却等不到结尾时，**宁可暂停发射也不把思考过程漏出去**。等后续 chunk 补齐 `</think>`，游标一跳，思考段整体蒸发。函数返回 `(generator, get_summary)` 二元组也很讲究：generator 供 agent.py 逐 chunk 转成 `task_summary_chunk` 事件推前端，`get_summary` 闭包在流耗尽后取完整文本存进 `task.summary`——**一次生成，两处消费**（实时展示 + 状态留档）。

## 🧅 第四层：reporter.py——把全部战果摊在报告专家面前（第 22-76 行）

`generate_report` 的本质是**造一个超长提示词**：

```python
for task in state.todo_items:
    tasks_block.append(
        f"### 任务 {task.id}: {task.title}\n"
        f"- 任务目标：{task.intent}\n"
        f"- 检索查询：{task.query}\n"
        f"- 执行状态：{task.status}\n"
        f"- 任务总结：\n{summary_block}\n"
        f"- 来源概览：\n{sources_block}\n"
    )
```

每条任务的四件套（目标 / 状态 / 总结 / 来源）依次摊开，后面再附一张**笔记索引**（"任务 1《背景梳理》：note_id=xxx"），并在提示词里给出 read 模板，请报告专家逐条读笔记后再动笔。也就是说，报告专家有两条信息渠道：提示词里的任务总结（推给它的）+ 笔记里的完整记录（它自己拉的）——推拉结合，防止总结压缩时丢了细节。

输出照例过两道清洗：`strip_thinking_tokens` + `strip_tool_calls`，兜底文案"报告生成失败，请检查输入。"。`text_processing.py` 全文只有一个正则 `\[TOOL_CALL:[^\]]+\]`——工具调用标记已经被框架执行过了，残留在正文里只会吓到用户，一律抹掉。

## 🧅 第五层：tool_events.py——书记员如何知道"这次调用是谁的"（第 41-215 行）

`ToolCallTracker.record` 被挂在每个 Agent 的 `tool_call_listener` 上，模型每调一次 note 工具它就记一笔。但工具调用的 payload 里只有参数和结果，**没有任务编号**——书记员要自己推理归属，`_infer_task_id`（第 181-206 行）三招连环：

```python
if "task_id" in parameters: return int(parameters["task_id"])   # ① 参数里直接有
for tag in tags:                                                 # ② 从 tags 里抓 task_(\d+)
    match = re.search(r"task_(\d+)", str(tag))
for title:                                                       # ③ 从标题里抓 "任务 N"
    match = re.search(r"任务\s*(\d+)", title)
```

现在回头看提示词里那句"`tags` 必须包含 `task_{task_id}`"——**提示词埋的钩子，在这里被代码收线**。同理 `_extract_note_id`（第 208-215 行）用 `ID:\s*([^\n]+)` 从 NoteTool 的返回文本里抠出新建笔记的 ID。

事件的消费有推拉两条路：

- **拉（drain，第 91-113 行）**：游标 `_cursor` 之后的新事件被批量取走，同时干一件要紧的副业——`_attach_note_to_task`：发现某任务的笔记 ID 后**回写到 TodoItem 上**（`task.note_id` / `task.note_path`）。前端任务卡片上"笔记：note_xxx，路径可复制"的小徽章，数据就从这来。
- **推（set_event_sink，第 140-143 行）**：流式模式下注册回调，`record` 的最后直接 `sink(payload)`，事件零延迟入队。

所有读写都在 `self._lock` 里——多个任务线程会并发调用 `record`，锁是必须的。

## 🧅 洋葱心：笔记即协作总线

把五个文件拼起来，得到本篇真正的一句话：

```
规划专家 --create--> notes/task_1.md <--read/update-- 总结专家
                          |
                          `----read----> 报告专家 --create--> notes/研究报告.md
                          |
     每一次 create/read/update 都被 ToolCallTracker 记录
                          |
                          v
              tool_call 事件 → SSE → 前端"工具调用记录"面板
```

笔记同时扮演三个角色：**跨 Agent 的通信信道**（专家之间不共享对话历史，共享文件）、**持久化的中间记忆**（服务重启后 notes/ 目录还在，可追溯每个任务的推理过程）、**可观测性的探针**（每次读写都变成前端可见的事件）。一个 NoteTool，吃下了消息队列、缓存、审计日志三份工作。

## 🎯 剥完之后：它在本章的位置

至此后端流水线全部接通：

```
planner 拆题 → search 找料 → summarizer 提炼(写笔记) → reporter 汇总(读笔记) → 报告
                                    ↑___________________↑
                              notes/ 目录 = 中间记忆
              全程 tool_events 记账 → 事件流 → 前端
```

chapter4 的 Plan-and-Solve 里，Planner 和 Executor 靠一个 Python 变量传计划；本章把这个变量升级成了磁盘上的笔记系统——**当协作方从"同一进程里的两个函数"变成"多线程里的多个 LLM 会话"，中间记忆就必须外置、持久、可寻址**。这是从玩具到工程最典型的一步。最后一篇看前端：这条事件流的另一端，如何变成用户眼里的实时研究界面。
