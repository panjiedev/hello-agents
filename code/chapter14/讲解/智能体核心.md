# agent.py + prompts.py 剥洋葱式讲解

> 源文件：
> - `code/chapter14/helloagents-deepresearch/backend/src/agent.py`（552 行）
> - `code/chapter14/helloagents-deepresearch/backend/src/prompts.py`（111 行）
>
> 一句话概括：**`DeepResearchAgent` 是本章的灵魂——它用三个提示词捏出三位专家（规划、总结、报告），再用一套"待办清单 + 并发执行 + 事件队列"的编排逻辑，把一个提问变成一份带引用、带笔记的研究报告。**

---

## 🧅 第一层（最外层）：这两个文件在干什么？

如果把 chapter4 的三种范式类比一下：DeepResearch 本质是一个**放大版的 Plan-and-Solve**——先规划、后执行、再汇总。但它把每个环节都升级了：

- 规划不再是一段自然语言计划，而是**结构化的 JSON 待办清单**（TodoItem）；
- 执行不再是逐步串行，而是**每个任务一个线程并发跑**，每个任务内部又是"搜索 → 总结"两拍；
- 中间结果不再只留在内存里，而是通过 **NoteTool 写成 Markdown 笔记**，供后续 Agent 读取；
- 整个过程不再是黑盒，而是**逐事件 yield 出来**，实时推到前端。

`prompts.py` 定义三位专家的人设，`agent.py` 负责雇佣他们并主持整场研究。先看人设，再看编排。

---

## 🧅 第二层：prompts.py——三位专家的"岗位说明书"

**① 研究规划专家 `todo_planner_system_prompt`（第 10-36 行）**

> "把复杂主题拆解为一组有限、互补的待办任务……梳理 3~5 个最关键的调研任务……任务之间要避免重复，整体覆盖用户的问题域。"

配套的用户级模板 `todo_planner_instructions`（第 39-60 行）规定了严格的输出协议：

```
请严格以 JSON 格式回复：
{"tasks": [{"title": "...", "intent": "...", "query": "..."}]}
```

`title` 给人看、`intent` 说明这个任务解决什么问题、`query` 直接喂给搜索引擎——一条任务三个字段，正好对应 `TodoItem` 的三个核心属性。还留了逃生门："如果主题信息不足以规划任务，请输出空数组"。

**② 任务总结专家 `task_summarizer_instructions`（第 63-84 行）**

> "针对任务意图梳理 3-5 条关键发现……从原理、应用、优缺点、工程实践、对比、历史演变等角度进行拓展。"

**③ 报告撰写专家 `report_writer_instructions`（第 87-110 行）**

给出了五段式报告模板：背景概览 → 核心洞见 → 证据与数据 → 风险与挑战 → 参考来源，并要求"引用来源时使用任务标题或来源标题，确保可追溯"。

三份提示词有一个贯穿始终的共同段落——`<NOTE_COLLAB>` / `<NOTES>`，都在教模型用同一种语法调用笔记工具：

```
[TOOL_CALL:note:{"action":"create","task_id":1,"title":"任务 1: 背景梳理",
 "note_type":"task_state","tags":["deep_research","task_1"],"content":"..."}]
```

这就是 chapter4 那条铁律"**提示词定协议，代码做解析**"的第四次落地：`[TOOL_CALL:note:{...}]` 是提示词与 HelloAgents 框架 `ToolAwareSimpleAgent` 约定的工具调用语法。注意 `tags` 必须含 `deep_research` 和 `task_{id}`——这不是装饰，后面会看到代码靠这两个标签**反推出每次工具调用属于哪个任务**。同时三份提示词都强调"最终呈现给用户的内容中禁止残留 `[TOOL_CALL:...]`"，而代码侧仍准备了 `strip_tool_calls` 兜底——提示词管期望，代码管底线。

## 🧅 第三层：`__init__`——一个 LLM，三个分身（第 35-74 行）

```python
self.todo_agent = self._create_tool_aware_agent(
    name="研究规划专家", system_prompt=todo_planner_system_prompt.strip())
self.report_agent = self._create_tool_aware_agent(
    name="报告撰写专家", system_prompt=report_writer_instructions.strip())
self._summarizer_factory = lambda: self._create_tool_aware_agent(
    name="任务总结专家", system_prompt=task_summarizer_instructions.strip())
```

三位专家共享同一个 `HelloAgentsLLM` 实例（`_init_llm`，第 79-107 行，按 provider 分支处理 ollama / lmstudio / 自定义服务，`temperature=0.0` 保证输出可解析），只是系统提示词不同——**"多智能体"在实现上常常只是"多提示词"**。

一个耐人寻味的差异：规划专家、报告专家是**单例**，总结专家却是**工厂函数**。原因在 `run_stream` 里——多个任务的总结要在多线程里**并发**跑，`ToolAwareSimpleAgent` 带对话历史、非线程安全，所以每个任务现场造一个新的总结专家，用完即弃（配合 `clear_history()`）。

`_create_tool_aware_agent`（第 109-118 行）还给每位专家挂了两样东西：注册了 NoteTool 的 `tool_registry`（他们唯一的工具就是记笔记），和 `tool_call_listener=self._tool_tracker.record`——每当模型真的调用了工具，事件立刻被 `ToolCallTracker` 记下（详见服务层篇），这是"工具调用记录"能显示在前端的源头。

## 🧅 第四层：`run`——研究状态机的骨干（第 125-148 行）

先看不带流式的同步版本，整个状态机一目了然：

```python
def run(self, topic: str) -> SummaryStateOutput:
    state = SummaryState(research_topic=topic)
    state.todo_items = self.planner.plan_todo_list(state)   # ① 规划
    if not state.todo_items:
        state.todo_items = [self.planner.create_fallback_task(state)]  # 规划失败兜底
    for task in state.todo_items:
        self._execute_task(state, task, emit_stream=False)  # ② 逐任务执行
    report = self.reporting.generate_report(state)          # ③ 汇总成报告
    self._persist_final_report(state, report)               # ④ 报告落盘为笔记
    return SummaryStateOutput(report_markdown=report, todo_items=state.todo_items)
```

**规划 → 执行 → 报告 → 落盘**，四步。而 `_execute_task`（第 289-413 行）内部是每个任务自己的小状态机：

```
pending → in_progress → dispatch_search 搜索
   ├─ 搜不到结果 → skipped（提前 return）
   └─ 搜到结果 → prepare_research_context 整理上下文
        → 写入 state（web_research_results / sources_gathered，加 self._state_lock 锁）
        → summarizer 总结 → completed
```

注意第 354-357 行的 `with self._state_lock:`——同步模式下没必要，但同一个函数也被流式模式的多线程复用，共享的 `SummaryState` 列表追加必须加锁。`emit_stream` 参数让这个函数一鱼两吃：`False` 时安静执行，`True` 时变成生成器，把每一步都 yield 成事件。

## 🧅 第五层：`run_stream`——多线程 + 队列，把并发折叠成一条事件流（第 150-284 行）

这是全文件最精彩的一段。难题是：N 个任务并发执行，各自随时产生事件，而 SSE 只有**一条**顺序的下行通道。解法是经典的**生产者-消费者**：

```python
event_queue: Queue[dict[str, Any]] = Queue()

def worker(task: TodoItem, step: int) -> None:       # 生产者 × N
    try:
        enqueue({"type": "task_status", "status": "in_progress", ...}, task=task)
        for event in self._execute_task(state, task, emit_stream=True, step=step):
            enqueue(event, task=task)
    except Exception as exc:
        enqueue({"type": "task_status", "status": "failed", ...}, task=task)
    finally:
        enqueue({"type": "__task_done__", "task_id": task.id})   # 哨兵

for task in state.todo_items:
    Thread(target=worker, args=(task, step), daemon=True).start()

while finished_workers < active_workers:              # 消费者 × 1
    event = event_queue.get()
    if event.get("type") == "__task_done__":
        finished_workers += 1
        continue
    yield event
```

三个细节：

1. **哨兵事件 `__task_done__`**：每个 worker 无论成功失败，`finally` 里必发一枚哨兵。主循环数够 N 枚哨兵才退出——这是不用 `join()` 阻塞、又能确定"所有人干完了"的标准手法（哨兵本身被吞掉，不会漏给前端）。
2. **`enqueue` 里的通道路由**（第 176-194 行）：开工前给每个任务分配了 `channel_map = {task.id: {"step": 序号, "token": "task_N"}}`，每个事件入队时自动盖上 `task_id` / `step` / `stream_token` 三枚章。前端正是靠 `task_id` 把混在一条流里的事件分拣回各自的任务卡片——**并发在后端，分拣在前端，事件里的 task_id 是接头暗号**。
3. **工具事件双模式**：流式模式下 `_set_tool_event_sink(tool_event_sink)` 让 ToolCallTracker 每记录一次工具调用就**立刻**入队（实时推送）；同步模式下则靠 `_drain_tool_events` 批量捞取。同一个 tracker，推/拉两种消费方式。

事件按时间顺序大致长这样（也就是前端将收到的剧本）：

```
status("初始化研究流程") → todo_list(全部任务)
→ [并发交织] task_status(in_progress) / tool_call / sources / task_summary_chunk×N / task_status(completed)
→ report_note → final_report → done
```

## 🧅 洋葱心：`_persist_final_report` 的"先更新、后创建"（第 447-503 行）

```python
note_id = self._find_existing_report_note_id(state)
if note_id:
    response = self.note_tool.run({"action": "update", "note_id": note_id, ...})
    if response.startswith("❌"):
        note_id = None
if not note_id:
    response = self.note_tool.run({"action": "create", ...})
    note_id = self._extract_note_id_from_text(response)
```

为什么报告落盘要绕这么大圈？因为**报告专家自己可能已经建过 conclusion 笔记**（提示词里教过它）。`_find_existing_report_note_id`（第 505-534 行）倒序翻查 ToolCallTracker 的历史：找 `tool == "note"`、`action` 是 create/update、`note_type == "conclusion"`（或标题以"研究报告"开头）的调用，从参数或返回文本里抠出 note_id。找到就 update 避免重复建档；update 失败（返回以 `❌` 开头——又一个文本协议）再退回 create。

这几行浓缩了本项目最核心的设计张力：**LLM 的行为是概率性的**（它可能建了笔记、可能没建、可能格式不对），**代码必须用确定性的逻辑把每种可能都接住**。规划失败有 fallback task，搜索失败有 skipped 状态，报告笔记有先查后建——整个 agent.py 就是一张为不可靠的 LLM 铺设的安全网。

## 🎯 剥完之后：它在本章的位置

`DeepResearchAgent` 是全项目的中枢，它对上服务 `main.py` 的两个接口，对下指挥四个服务：

| 协作方 | 关系 |
|---|---|
| `PlanningService` | 把话筒递给规划专家，把 JSON 解析成 TodoItem（下一篇） |
| `dispatch_search` | 每个任务的"眼睛"，负责联网找材料（下一篇） |
| `SummarizationService` | 每个任务的"笔"，流式产出总结（再下一篇） |
| `ReportingService` | 收官的"主编"，整合所有任务写报告（再下一篇） |
| `ToolCallTracker` | 全程"书记员"，记录每次笔记操作并转成事件（再下一篇） |

一句话总结它的编排哲学：**提示词负责"想"（拆题、总结、写报告），服务负责"做"（搜索、解析、落盘），agent.py 负责"排"（谁先谁后、并发几路、事件怎么流）**——想、做、排三权分立，是所有生产级智能体系统的共同骨相。
