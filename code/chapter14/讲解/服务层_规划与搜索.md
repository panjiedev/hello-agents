# services/planner.py + search.py 剥洋葱式讲解

> 源文件：
> - `code/chapter14/helloagents-deepresearch/backend/src/services/planner.py`（161 行）
> - `code/chapter14/helloagents-deepresearch/backend/src/services/search.py`（98 行）
>
> 一句话概括：**planner 把"一个模糊的研究主题"变成"3~5 条可执行的待办任务"，search 把"一条任务的 query"变成"一堆整理好的网页材料"——一个管拆题，一个管找料。**

---

## 🧅 第一层（最外层）：这两个文件在干什么？

回想一次人工的深度调研：拿到题目后，你会先在纸上列出"我需要搞清楚哪几个问题"（规划），然后对每个问题去搜索引擎找资料（检索）。这两个文件就是这两步的代码化：

- `PlanningService`：包住"研究规划专家"Agent，负责发问、**解析**它吐出的 JSON、失败时兜底。
- `dispatch_search` + `prepare_research_context`：包住 HelloAgents 的 `SearchTool`，负责调后端搜索、规整五花八门的返回格式。

它们的共同职责用一个词概括：**归一化（normalization）**。LLM 的输出格式不可靠，搜索后端的返回格式不统一，这两个文件把混沌的外部世界整理成 agent.py 能放心消费的干净结构。

---

## 🧅 第二层：`plan_todo_list`——一问一答一解析（planner.py 第 31-67 行）

```python
prompt = todo_planner_instructions.format(
    current_date=get_current_date(),
    research_topic=state.research_topic,
)
response = self._agent.run(prompt)
self._agent.clear_history()

tasks_payload = self._extract_tasks(response)
for idx, item in enumerate(tasks_payload, start=1):
    title = str(item.get("title") or f"任务{idx}").strip()
    intent = str(item.get("intent") or "聚焦主题的关键问题").strip()
    query = str(item.get("query") or state.research_topic).strip()
    todo_items.append(TodoItem(id=idx, title=title, intent=intent, query=query))
```

三个细节：

1. **提示词里注入了当前日期**——研究"最新进展"类主题时，模型知道今天是哪天才不会把两年前的新闻当新料。
2. **`clear_history()`**：规划专家是单例，每次规划完立刻清空对话历史，防止上一个研究主题的记忆污染下一个请求——无状态服务的纪律。
3. **每个字段都有 `or` 兜底**：模型漏了 title 就叫"任务N"，漏了 query 就直接拿研究主题去搜。宁可任务糙一点，也不让流程断掉。

规划彻底失败时还有终极兜底 `create_fallback_task`（第 69-78 行）：造一条"基础背景梳理"任务，query 是 `"{主题} 最新进展"`——保证状态机至少能走完一圈。

## 🧅 第三层：`_extract_tasks`——三层解析瀑布（planner.py 第 83-160 行）

提示词要求"严格以 JSON 格式回复"，但**永远不要指望模型严格**。解析器准备了三道防线：

**防线一：先剥思考再找 JSON。** `strip_thinking_tokens` 去掉 `<think>` 段，然后 `_extract_json_payload`（第 113-134 行）用最朴素也最皮实的办法定位 JSON：

```python
start = text.find("{")
end = text.rfind("}")
if start != -1 and end != -1 and end > start:
    candidate = text[start : end + 1]
    try:
        return json.loads(candidate)
    except json.JSONDecodeError:
        pass
```

第一个 `{` 到最后一个 `}`——不管模型在 JSON 前后包了多少客套话、代码围栏，都能切出来。对象解析失败再试数组（`[` 到 `]`）。

**防线二：JSON 找不到，去工具调用里翻。** 有些模型不直接回 JSON，而是把任务清单塞进了 `[TOOL_CALL:note:{...}]` 里。`_extract_tool_payload`（第 136-160 行）用正则 `TOOL_CALL_PATTERN` 抓第一个工具调用，解析它的 body，看里面有没有 `tasks` 列表。

**防线三：body 连 JSON 都不是？** 还按 `key=value, key=value` 的格式再拆一次（第 152-158 行）。

三道防线全空手而归，才轮到上一层的 fallback task。这一小节是"**代码做解析**"的教科书样本：协议写在提示词里，但兑现协议的责任全在解析器——**解析器的健壮程度决定了系统能兼容多弱的模型**。

## 🧅 第四层：`dispatch_search`——把五种搜索后端归一成一个 payload（search.py 第 23-77 行）

```python
_GLOBAL_SEARCH_TOOL = SearchTool(backend="hybrid")   # 模块级单例

raw_response = _GLOBAL_SEARCH_TOOL.run({
    "input": query,
    "backend": search_api,        # 用户选的：tavily/duckduckgo/perplexity/searxng/advanced
    "mode": "structured",
    "fetch_full_page": config.fetch_full_page,
    "max_results": 5,
    "max_tokens_per_source": MAX_TOKENS_PER_SOURCE,   # 2000
    "loop_count": loop_count,
})
```

搜索的脏活（调 API、限流、降级切换后端）全部下沉给了 HelloAgents 框架的 `SearchTool`（`backend="hybrid"` 表示允许它在配置的后端不可用时自动换路）。本文件只做**返回值归一化**（第 48-59 行）：

```python
if isinstance(raw_response, str):
    # 返回字符串 = 出事了（配额耗尽、后端不可用），当作 notice 处理
    notices = [raw_response]
    payload = {"results": [], "backend": search_api, "answer": None, "notices": notices}
else:
    payload = raw_response
    notices = list(payload.get("notices") or [])
```

又是文本协议：`SearchTool` 用"返回 str 还是 dict"区分"故障通告"和"正常结果"。归一化后统一返回四元组 `(payload, notices, answer_text, backend_label)`——notices 会作为"系统提示"事件推给前端（用户能看到"Tavily 配额不足，已切换 DuckDuckGo"这类信息），`backend_label` 告诉前端实际用了哪个引擎（可能和用户选的不同，因为降级了），`answer_text` 是 Perplexity 这类引擎附带的 AI 直答。

## 🧅 洋葱心：`prepare_research_context` 的双轨输出（search.py 第 80-97 行）

```python
sources_summary = format_sources(search_result)            # 给人看的短清单
context = deduplicate_and_format_sources(                  # 给 LLM 吃的长文本
    search_result or {"results": []},
    max_tokens_per_source=MAX_TOKENS_PER_SOURCE,
    fetch_full_page=config.fetch_full_page,
)
if answer_text:
    context = f"AI直接答案：\n{answer_text}\n\n{context}"
return sources_summary, context
```

同一份搜索结果，一次加工出**两种视图**：

- `sources_summary`（`* 标题 : URL` 清单）→ 存进 `task.sources_summary` → 推给前端渲染成可点击的引用列表，也进入最终报告的"参考来源"节；
- `context`（去重后的全文长稿，每源截断 2000 token）→ 喂给总结专家做深度提炼。

如果搜索引擎给了 AI 直答，就把它顶在 context 最前面——相当于给总结专家先递一份"摘要版"，再附全文。**引用的可追溯性和总结的信息密度，靠的就是这两轨分离。**

## 🎯 剥完之后：它在本章的位置

在"提问 → 报告"的流水线上，这两个文件是最前面的两站：

```
研究主题
  → PlanningService.plan_todo_list()      拆成 3~5 条 TodoItem
  → 对每条任务：dispatch_search(query)     搜回原始材料
  → prepare_research_context()             整理成 (引用清单, LLM上下文)
  → 交给 SummarizationService              （下一篇）
```

两个文件各自守着一条边界：planner 守**LLM 输出 → 程序数据**的边界（靠三层解析瀑布），search 守**外部 API → 程序数据**的边界（靠返回值归一化）。边界守干净了，agent.py 的编排逻辑才能写得那么直白。
