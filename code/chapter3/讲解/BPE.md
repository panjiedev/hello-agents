# BPE.py 剥洋葱式讲解

> 源文件：`code/chapter3/BPE.py`（34 行）
> 一句话概括：**手写一个迷你版 BPE（Byte Pair Encoding，字节对编码）算法——GPT、Qwen 等大模型的分词器（Tokenizer）就是靠它构建词表的。**

---

## 🧅 第一层（最外层）：这个文件在干什么？

模型不认识"单词"，只认识数字。把文本切成模型认识的最小单位（词元/token）是一切的第一步。但词表怎么定？

- 按**完整单词**建词表 → 词表爆炸，且遇到新词（如 "hugging"）就傻眼；
- 按**单个字符**建词表 → 词表极小，但序列太长，且字符本身没含义。

BPE 走中间路线：**从字符出发，反复把"最常一起出现的相邻词元对"合并成新词元**，让高频组合（如 `ug`）自动"长"成词表里的一员。

运行这个脚本，你会看到 4 轮合并的过程，词表从纯字符逐步"生长"出 `ug`、`un`、`hug` 这些子词（subword）。

---

## 🧅 第二层：主循环——训练 BPE 的完整流程

剥开一层看第 22-34 行的主程序：

```python
vocab = {'h u g </w>': 1, 'p u g </w>': 1, 'p u n </w>': 1, 'b u n </w>': 1}
num_merges = 4

for i in range(num_merges):
    pairs = get_stats(vocab)          # ① 统计所有相邻词元对的频率
    best = max(pairs, key=pairs.get)  # ② 找出现最多的那一对
    vocab = merge_vocab(best, vocab)  # ③ 把这一对合并成一个新词元
```

**语料的表示方式**是理解的关键：

- 语料库是 4 个词：hug、pug、pun、bun，各出现 1 次（字典的 value 是词频）；
- 每个词已经**用空格切成单个字符**——空格是"词元边界"的记号；
- 末尾的 `</w>` 表示"词的结束"，让模型能区分 "un" 出现在词尾（b-un）还是词中。

整个训练就是重复"**数一数 → 挑最多 → 合并**"这三板斧，合并几次，词表里就多几个新词元。真实的大模型分词器（如 GPT-2 的 50257 词表）就是把这个循环跑了几万次。

---

## 🧅 第三层：两个函数——"数数"和"合并"

### `get_stats(vocab)`：统计相邻词元对的频率（第 3-10 行）

```python
for word, freq in vocab.items():
    symbols = word.split()
    for i in range(len(symbols)-1):
        pairs[symbols[i], symbols[i+1]] += freq
```

对每个词，把相邻两个词元配成对，累加词频。以初始词表为例：

```
h u g  → (h,u)+1  (u,g)+1
p u g  → (p,u)+1  (u,g)+1   ← (u,g) 累计到 2
p u n  → (p,u)+1  (u,n)+1   ← (p,u) 累计到 2
b u n  → (b,u)+1  (u,n)+1   ← (u,n) 累计到 2
```

`(u,g)`、`(p,u)`、`(u,n)` 并列最高频（都是 2），`max` 会取第一个遇到的 `(u,g)`。

### `merge_vocab(pair, v_in)`：执行合并（第 12-20 行）

把词表里所有 `u g`（中间有空格 = 两个独立词元）替换成 `ug`（无空格 = 一个词元）：

```
'h u g </w>'  →  'h ug </w>'
'p u g </w>'  →  'p ug </w>'
```

删掉空格，两个词元就"焊"成了一个——这就是 BPE 中 "merge" 的全部含义。

## 🧅 第四层（洋葱心）：那个正则表达式

```python
bigram = re.escape(' '.join(pair))            # 'u g'  →  'u\ g'
p = re.compile(r'(?<!\S)' + bigram + r'(?!\S)')
p.sub(''.join(pair), word)                    # 'u g' → 'ug'
```

为什么不直接用 `word.replace('u g', 'ug')`？因为会误伤。剥开这三行：

- `re.escape`：词元里可能含 `.`、`*` 等正则特殊字符（真实语料中很常见），转义后才能按字面匹配。
- `(?<!\S)`：**后行断言**，"前面不能是非空白字符"——保证匹配从一个完整词元的开头开始。
- `(?!\S)`：**先行断言**，"后面不能是非空白字符"——保证匹配到一个完整词元的结尾为止。

举个会出错的例子：假设经过前几轮合并，某个词现在是 `'h hu g'`（三个词元：`h`、`hu`、`g`），现在要合并的对是 `(u, g)`。如果简单地 `'h hu g'.replace('u g', 'ug')`，会匹配到词元 `hu` 的尾巴 `u` 加上后面的 `g`，得到 `'h hug'`——凭空把 `hu` 拆了。而 `(?<!\S)` 要求匹配的 `u` 前面必须是空白（即 `u` 是一个完整词元的开头），这里 `u` 前面是 `h`，匹配失败，避免了误合并。断言保证了只有**完整的词元 u + 完整的词元 g** 才会被合并。

一句话：这对断言就是"**整词元匹配**"的保险丝。

## 🎯 剥完之后：运行结果与全局意义

4 轮合并依次产生：`ug`（u+g）→ `un`（u+n）→ `hug`（h+ug）→ `pug`（p+ug）。

这个 30 行的玩具和 GPT 用的真实 BPE 只有规模差异，没有原理差异：

1. **训练阶段**（本脚本演示的）：在海量语料上跑几万轮合并，得到词表 + 合并规则表；
2. **推理阶段**：对新文本先切成字符，再按学到的合并规则**依次重放**，就能把任何词（包括没见过的新词）切成词表内的子词——这就是大模型"永远不会遇到词表外单词"的原因。

在 `Qwen.py` 里调用的 `AutoTokenizer`，内部正是这套机制的工业级实现。
