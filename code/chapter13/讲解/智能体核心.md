# trip_planner_agent.py 剥洋葱式讲解

> 源文件：`code/chapter13/helloagents-trip-planner/backend/app/agents/trip_planner_agent.py`（430 行）
> 一句话概括：**本章的灵魂文件——用四个各司其职的 SimpleAgent（景点搜索、天气查询、酒店推荐、行程规划）流水线协作，把用户的一句需求变成一份可被 Pydantic 校验的结构化 JSON 行程。**

---

## 🧅 第一层（最外层）：这个文件在干什么？

前面的章节里，智能体在终端里"自娱自乐"；到了真实产品里，智能体必须回答一个新问题：**它的输出要给谁用？**

答案是：给前端渲染地图、卡片、预算表用。这就意味着 LLM 不能再输出随意的自然语言，而必须输出**严格结构化的 JSON**。整个文件就是围绕这个矛盾展开的：

```python
planner = get_trip_planner_agent()          # 单例：四个 Agent + 一个 MCP 工具
trip_plan = planner.plan_trip(request)      # 传入 TripRequest，返回 TripPlan 对象
```

对外只有一个方法 `plan_trip`，内部却是一条四步流水线：**搜景点 → 查天气 → 找酒店 → 汇总规划**。前三步负责"采集真实世界的数据"（调高德地图），第四步负责"把数据编排成行程"（纯 LLM 推理）。

---

## 🧅 第二层：四段提示词——每个 Agent 一张"岗位说明书"（第 13-152 行）

文件开头 140 行全是提示词，这不是凑数——**多智能体系统的分工，全部写在提示词里**。前三个 Agent 的提示词结构完全相同，以景点搜索为例（第 13-33 行）：

```python
ATTRACTION_AGENT_PROMPT = """你是景点搜索专家。...

**重要提示:**
你必须使用工具来搜索景点!不要自己编造景点信息!

**工具调用格式:**
`[TOOL_CALL:amap_maps_text_search:keywords=景点关键词,city=城市名]`

**示例:**
用户: "搜索北京的历史文化景点"
你的回复: [TOOL_CALL:amap_maps_text_search:keywords=历史文化,city=北京]
...
"""
```

三个要素缺一不可：

1. **"必须使用工具，不要编造"**——这是在对抗 LLM 的幻觉本能。旅行规划最怕模型自信地编出一个不存在的景点；
2. **`[TOOL_CALL:工具名:参数]` 协议**——HelloAgents 框架的 SimpleAgent 靠解析这个格式来触发 MCP 工具调用。又是那条老规矩：**提示词定协议，代码做解析**；
3. **少样本示例（few-shot）**——直接给两个"用户问 → 你答"的范例，比一百句格式说明都管用。

第四个提示词 `PLANNER_AGENT_PROMPT`（第 75-152 行）画风突变：它不要求调工具，而是**把一份完整的 JSON 模板原样贴进提示词**——从 `city`、`days`、每个景点的 `location: {"longitude": ..., "latitude": ...}` 到 `budget` 汇总，一个字段不落。这份模板和 `schemas.py` 里的 `TripPlan` 模型是**镜像关系**：提示词里长什么样，Pydantic 模型就校验什么样。这是"约束 LLM 输出结构化数据"最朴素也最有效的手法：**给模型看一遍你想要的形状**。

模板之后还有一串针对性补丁（第 140-152 行），比如"温度必须是纯数字(不要带°C等单位)"——每一条几乎都是被真实的解析失败"教育"出来的经验。

## 🧅 第三层：`__init__`——一个工具，四个专家（第 158-221 行）

```python
self.amap_tool = MCPTool(
    name="amap",
    server_command=["uvx", "amap-mcp-server"],
    env={"AMAP_MAPS_API_KEY": settings.amap_api_key},
    auto_expand=True
)
```

MCP 工具**只创建一次**（第 168-175 行），然后被三个采集类 Agent 共享——`MCPTool` 背后是一个通过 `uvx` 拉起的高德 MCP 服务器子进程，创建三份就是三个子进程，纯属浪费。`auto_expand=True` 会把 MCP 服务器暴露的十几个工具（`maps_text_search`、`maps_weather`……）自动展开成独立可调用的工具。

四个 Agent 的创建方式如出一辙，差异只有两处：

| Agent | 系统提示词 | 带不带工具 |
|---|---|---|
| 景点搜索专家 | ATTRACTION_AGENT_PROMPT | ✅ amap_tool |
| 天气查询专家 | WEATHER_AGENT_PROMPT | ✅ amap_tool |
| 酒店推荐专家 | HOTEL_AGENT_PROMPT | ✅ amap_tool |
| 行程规划专家 | PLANNER_AGENT_PROMPT | ❌ 无工具 |

**同一个 LLM、同一个工具，换一份提示词就是另一个专家**——这正是 chapter4 结尾那句话（"智能体的能力不在代码里，在提示词里"）在真实项目中的落地。规划 Agent 不带工具，因为它的原料由前三个 Agent 供给，它只需要专心"编排"。

## 🧅 第四层：`plan_trip`——四步流水线（第 242-267 行）

```python
# 步骤1: 景点搜索Agent搜索景点
attraction_response = self.attraction_agent.run(attraction_query)
# 步骤2: 天气查询Agent查询天气
weather_response = self.weather_agent.run(f"请查询{request.city}的天气信息")
# 步骤3: 酒店推荐Agent搜索酒店
hotel_response = self.hotel_agent.run(f"请搜索{request.city}的{request.accommodation}酒店")
# 步骤4: 行程规划Agent整合信息生成计划
planner_query = self._build_planner_query(request, attraction_response, weather_response, hotel_response)
planner_response = self.planner_agent.run(planner_query)
```

这是最简单的多智能体编排——**顺序流水线**：前三步的输出（自然语言 + 工具返回的真实 POI 数据）被 `_build_planner_query`（第 294-326 行）拼进第四步的输入里，成为规划 Agent 的"素材库"。没有消息总线、没有黑板机制，就是字符串拼接，但它清晰地演示了多智能体协作的本质：**上游 Agent 的输出是下游 Agent 的上下文**。

一个耐人寻味的细节在 `_build_attraction_query`（第 281-292 行）：

```python
query = f"请使用amap_maps_text_search工具搜索{request.city}的{keywords}相关景点。\n[TOOL_CALL:amap_maps_text_search:keywords={keywords},city={request.city}]"
```

查询文本里**直接预埋了一条现成的 TOOL_CALL**——相当于不赌 LLM 会不会正确发起调用，代码先替它把调用写好。这是工程上的"保送"：提示词教了格式，查询里再塞一个标准答案，双保险确保第一步的工具调用万无一失。

整个 `plan_trip` 被 try/except 包住（第 275-279 行），任何一步崩了就落到 `_create_fallback_plan`——**用户永远能拿到一份行程，哪怕是占位的**。

## 🧅 洋葱心：`_parse_response` 的解析瀑布（第 342-362 行）

LLM 说完了，最惊险的一步才开始——把一段自由文本变成程序能用的对象：

```python
if "```json" in response:
    json_start = response.find("```json") + 7
    json_end = response.find("```", json_start)
    json_str = response[json_start:json_end].strip()
elif "```" in response:
    ...                                    # 退而求其次：任意代码块
elif "{" in response and "}" in response:
    json_start = response.find("{")
    json_end = response.rfind("}") + 1     # 最宽松：首个 { 到最后一个 }
    json_str = response[json_start:json_end]
else:
    raise ValueError("响应中未找到JSON数据")

data = json.loads(json_str)
trip_plan = TripPlan(**data)
```

三级解析瀑布，宽容度逐级放大：标准 ` ```json ` 代码块 → 任意 ` ``` ` 代码块 → 裸 JSON 对象。因为 LLM 再听话也有"发挥"的时候——有时加代码块标记，有时不加，有时前后附赠一段客套话。

真正的守门员是最后一行 `TripPlan(**data)`：**Pydantic 模型逐字段校验 LLM 的输出**——缺了必填字段、类型对不上，立刻抛异常，绝不让一份残缺的行程流到前端。而 `WeatherInfo` 里的温度校验器还会顺手把 `"25°C"` 这类不听话的输出洗成 `25`（见"API 路由与数据模型"篇）。

解析失败怎么办？不崩，走 `_create_fallback_plan`（第 371-415 行）生成一份"景点1、景点2"式的占位行程。**LLM 是不可靠的组件，系统必须在它掉链子时优雅降级**——这是把智能体从 demo 变成产品的关键一课。

## 🎯 剥完之后：它在本章的位置

这个文件是"生成行程"链路的正中心：

> 前端表单 → `/api/trip/plan` 路由 → **`plan_trip` 四步流水线** → 高德 MCP（真实数据）+ LLM（编排推理）→ **解析瀑布 + Pydantic 校验** → TripPlan JSON → 前端地图渲染

它同时回答了本章的两个核心问题：

1. **多智能体怎么分工？**——一份提示词一个专家，顺序流水线传递上下文；
2. **LLM 输出怎么变成产品数据？**——提示词贴 JSON 模板定形状，解析瀑布捞 JSON，Pydantic 校验把关，fallback 兜底。

两头都体现同一条铁律：**对 LLM，既要给足格式约束（提示词侧），又要假设它随时会违约（解析侧）。**
