# 前端（frontend/src/）剥洋葱式讲解

> 源文件：`code/chapter13/helloagents-trip-planner/frontend/src/` 下的 `main.ts`（31 行）、`App.vue`（28 行）、`services/api.ts`（65 行）、`types/index.ts`（95 行）、`views/Home.vue`（649 行）、`views/Result.vue`（1434 行）
> 一句话概括：**Vue3 + TypeScript 的两页应用——Home 页收集需求发给后端，Result 页把 LLM 生成的 JSON 行程渲染成卡片、预算表和一张真正的高德地图。**

---

## 🧅 第一层（最外层）：这些文件在干什么？

后端再聪明，用户看到的永远是前端。整个前端只有两个页面、一条动线：

```
Home.vue（填表单）──axios POST──▶ 后端 /api/trip/plan
                                        │
Result.vue（渲染行程+地图）◀──sessionStorage──┘
```

骨架文件极薄：`main.ts` 注册两条路由（`/` → Home，`/result` → Result，第 9-23 行），`App.vue` 提供页头页脚的布局壳子。真正的戏份在另外四个文件：`api.ts` 管通信、`types/index.ts` 管类型、`Home.vue` 管输入、`Result.vue` 管输出。

---

## 🧅 第二层：api.ts 与 types/index.ts——通信层和类型层（api.ts 第 4-49 行）

```typescript
const apiClient = axios.create({
  baseURL: API_BASE_URL,
  timeout: 120000, // 2分钟超时
  ...
})
```

`timeout: 120000` 是全文件最能体现"智能体应用特色"的一个数字：普通接口 5 秒超时足矣，但这个请求背后是**四个 Agent 依次跑、每个都要调 LLM**，两分钟是给流水线留的余量。前端的参数里，藏着对后端架构的理解。

`generateTripPlan`（第 41-49 行）里的错误提取也和后端严丝合缝：

```typescript
throw new Error(error.response?.data?.detail || error.message || '生成旅行计划失败')
```

`data.detail` 正是 FastAPI `HTTPException` 的字段名——路由篇埋的暗号，在这里被接住。

`types/index.ts` 则是 `schemas.py` 的 TypeScript 镜像：`TripPlan`、`DayPlan`、`Attraction`、`Budget`……字段一一对应，连 `Optional` 都翻译成了 `?:`。**同一份数据形状的第三次出现**（提示词 → Pydantic → TypeScript），编辑器的自动补全和编译期检查由此而来。

## 🧅 第三层：Home.vue——表单、假进度条和 sessionStorage 接力（第 219-315 行）

表单本身是标准的 Ant Design Vue 三段式（目的地日期 / 偏好 / 额外要求），有意思的是三个交互细节：

**其一，天数自动计算**（第 231-244 行）：`watch` 监听起止日期，`end.diff(start, 'day') + 1` 算出天数，超过 30 天或倒序直接清空——**后端 `TripRequest` 里 `ge=1, le=30` 的约束，前端提前拦了一道**，用户不用等 422 才知道错。

**其二，"善意的谎言"进度条**（第 257-272 行）：

```typescript
const progressInterval = setInterval(() => {
  if (loadingProgress.value < 90) {
    loadingProgress.value += 10
    if (loadingProgress.value <= 30) {
      loadingStatus.value = '🔍 正在搜索景点...'
    } else if (loadingProgress.value <= 50) {
      loadingStatus.value = '🌤️ 正在查询天气...'
    } else if (loadingProgress.value <= 70) {
      loadingStatus.value = '🏨 正在推荐酒店...'
    } else {
      loadingStatus.value = '📋 正在生成行程计划...'
    }
  }
}, 500)
```

后端是同步接口，没有真实进度可推——于是前端每 500ms 自增 10%，卡在 90% 等真响应。妙在文案：**四段状态词正好对应后端流水线的四个步骤**（搜景点→查天气→找酒店→生成计划），进度是假的，剧情却是真的。等待一两分钟的用户，看到的是"AI 在一步步干活"而不是转圈的黑盒。

**其三，页面间的接力棒**（第 292-301 行）：

```typescript
sessionStorage.setItem('tripPlan', JSON.stringify(response.data))
router.push('/result')
```

没有引入 Pinia/Vuex 状态管理，就用 `sessionStorage` 把行程 JSON 递给下一页——两页应用够用就好，还白赚一个特性：Result 页刷新不丢数据。

## 🧅 第四层：Result.vue——把 JSON 变成一页可看、可改、可导出的行程

Result 页 1400 多行，剥掉样式和导出逻辑，主干是 `onMounted` 的三步（第 329-339 行）：

```typescript
const data = sessionStorage.getItem('tripPlan')
if (data) {
  tripPlan.value = JSON.parse(data)     // 1. 接过接力棒
  await loadAttractionPhotos()          // 2. 为每个景点异步取图
  await nextTick()
  initMap()                             // 3. 初始化高德地图
}
```

**取图**（第 428-451 行）：遍历所有景点，并发请求后端 `/api/poi/photo`（Unsplash 封装），`Promise.all` 等齐。图片没到位时，`getAttractionImage`（第 454-484 行）现场生成一张带景点名的渐变色 SVG 占位图，base64 内联——**页面永远不会出现破图**。

**初始化地图**（第 833-856 行）：`AMapLoader.load` 用前端自己的 JS API Key（注意：和后端的 Web 服务 Key 是两把钥匙）加载高德 SDK，创建 3D 地图实例。

此外还有**编辑模式**（第 355-415 行：改地址/时长/描述、上下移动、删除景点，保存写回 sessionStorage 并重建地图，取消则从深拷贝的 `originalPlan` 还原）和**导出**（html2canvas 截图 → PNG 或 jsPDF 分页成 PDF，第 496-787 行）——AI 生成的行程不是终点，而是用户可继续加工的草稿。

## 🧅 洋葱心：让 LLM 的数字落在地图上（Result.vue 第 866-916 行）

```typescript
tripPlan.value.days.forEach((day, dayIndex) => {
  day.attractions.forEach((attraction, attrIndex) => {
    if (attraction.location && attraction.location.longitude && attraction.location.latitude) {
      allAttractions.push({ ...attraction, dayIndex, attrIndex })
    }
  })
})

allAttractions.forEach((attraction, index) => {
  const marker = new AMap.Marker({
    position: [attraction.location.longitude, attraction.location.latitude],
    title: attraction.name,
    ...
  })
  ...
})
map.add(markers)
map.setFitView(markers)   // 自动缩放视野包住所有标记
```

这就是整条链路的"最后一公里"：**LLM 吐出的两个浮点数（经度、纬度），变成了地图上一枚可点击的图钉**。规划 Agent 提示词里那句"景点的经纬度坐标要真实准确"、高德 MCP 返回的真实 POI 数据、Pydantic 的 `Location` 模型——上游所有对坐标的较真，都是为了这一刻不出现"图钉插进海里"。

注意循环开头的坐标判空：哪怕前面层层把关，前端仍然只信"有完整经纬度"的景点——**每一层都不完全信任上一层**，这个原则贯穿了全栈。

随后 `drawRoutes`（第 924-956 行）按天分组，把同一天的景点用带方向箭头的蓝色折线串起来——每天的游览动线一目了然。

## 🎯 剥完之后：它在本章的位置

前端是"生成行程"链路的两端——起点和终点：

| 文件 | 在链路中的角色 |
|---|---|
| `Home.vue` | 起点：表单 → `TripFormData`，假进度条掩护后端流水线 |
| `api.ts` | 信使：axios + 120 秒超时，错误暗号对接 FastAPI |
| `types/index.ts` | 合同副本：`schemas.py` 的 TS 镜像 |
| `Result.vue` | 终点：JSON → 卡片 / 预算表 / 高德地图 / 可编辑 / 可导出 |

至此全链路闭环：**用户点一次按钮 → 四个 Agent 接力 → 高德 MCP 供真实数据 → LLM 编排成 JSON → 三道形状检查放行 → 地图上落下一排图钉。** LLM 的输出只有被渲染成用户能看、能改、能带走的东西，智能体才算真正交付了价值——这就是"全栈智能体应用"的含义。
