# 服务层（services/）剥洋葱式讲解

> 源文件：`code/chapter13/helloagents-trip-planner/backend/app/services/llm_service.py`（37 行）、`amap_service.py`（269 行）、`unsplash_service.py`（86 行）
> 一句话概括：**把三个外部世界——LLM、高德地图、Unsplash 图库——各封装成一个单例服务，让上层代码"要能力不问出处"。**

---

## 🧅 第一层（最外层）：这三个文件在干什么？

一个全栈智能体应用要跟很多"外面的东西"打交道：LLM 服务商、地图服务商、图片服务商。如果把这些调用散落在路由和 Agent 代码里，密钥、超时、错误处理就会到处复制粘贴。服务层的职责就是**把每个外部依赖包成一个类 + 一个 `get_xxx()` 单例工厂**：

```python
llm = get_llm()                      # LLM：智能体的"脑"
amap = get_amap_service()            # 高德地图：POI/天气/路线
unsplash = get_unsplash_service()    # Unsplash：景点配图
```

三个文件遵循同一个模板：模块级私有变量 `_xxx = None` → `get_xxx()` 第一次调用时创建、之后直接返回。**贵的资源（子进程、HTTP 连接、模型客户端）全进程只建一份。**

## 🧅 第二层：llm_service.py——最薄的一层封装（第 10-30 行）

```python
def get_llm() -> HelloAgentsLLM:
    global _llm_instance
    if _llm_instance is None:
        _llm_instance = HelloAgentsLLM()   # 配置全部从环境变量读取
        print(f"   提供商: {_llm_instance.provider}")
        print(f"   模型: {_llm_instance.model}")
    return _llm_instance
```

37 行里真正干活的不到 10 行——因为脏活累活 chapter4 就干完了：`HelloAgentsLLM` 自己会从 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL_ID` 读配置。这一层的价值只有两点：**单例**（四个 Agent 共享一个 LLM 客户端，而不是各建一个连接）和**统一入口**（将来要换模型、加缓存、记 token 账，只改这一个文件）。

还附送一个 `reset_llm()`（第 33-36 行）把单例置空——单例模式的常见配套：测试时需要"重开一局"。

## 🧅 第三层：amap_service.py——把 MCP 工具包成普通 Python 方法（第 12-47 行）

先看单例工厂里的核心：

```python
_amap_mcp_tool = MCPTool(
    name="amap",
    description="高德地图服务,支持POI搜索、路线规划、天气查询等功能",
    server_command=["uvx", "amap-mcp-server"],
    env={"AMAP_MAPS_API_KEY": settings.amap_api_key},
    auto_expand=True
)
```

这行代码背后发生的事远比它看起来多：`uvx` 会**拉起一个独立的 MCP 服务器子进程**（amap-mcp-server），密钥通过环境变量注入子进程，之后所有地图能力都走 MCP 协议与这个子进程通信。这就是为什么必须单例——每次 new 一个 `MCPTool` 就是一个新子进程。

`AmapService` 类再把 MCP 调用翻译成一个个语义清晰的方法：`search_poi`、`get_weather`、`plan_route`、`geocode`、`get_poi_detail`。其中 `plan_route`（第 122-186 行）有个典型的"参数翻译"逻辑：

```python
tool_map = {
    "walking": "maps_direction_walking_by_address",
    "driving": "maps_direction_driving_by_address",
    "transit": "maps_direction_transit_integrated_by_address"
}
tool_name = tool_map.get(route_type, "maps_direction_walking_by_address")
```

调用方只说"我要步行/驾车/公交"，服务层负责映射到高德真正的工具名——**外部 API 的命名细节被挡在服务层以内**。

另一个值得看的是 `get_poi_detail` 的结果解析（第 245-248 行）：

```python
json_match = re.search(r'\{.*\}', result, re.DOTALL)
if json_match:
    data = json.loads(json_match.group())
```

MCP 工具返回的是字符串，用正则捞出其中的 JSON——和智能体核心篇的"解析瀑布"是同一个思想的简化版。诚实地说，这个文件里 `search_poi` / `get_weather` / `plan_route` 的解析都还是 `TODO`（第 86-87、115-116、181-182 行），返回空列表/空字典——因为**本项目的主链路里，高德数据实际是由 Agent 通过 TOOL_CALL 直接消费的**（LLM 自己读工具返回的文本），`AmapService` 主要服务于 `/api/map/*` 这组"直通车"接口和 POI 详情查询。

## 🧅 第四层：unsplash_service.py——一个教科书式的 REST 封装（第 16-56 行）

高德走的是 MCP 协议，Unsplash 则演示了最传统的封装方式——`requests` 直调 REST API：

```python
url = f"{self.base_url}/search/photos"
params = {"query": query, "per_page": per_page, "client_id": self.access_key}

response = requests.get(url, params=params, timeout=10)
response.raise_for_status()
```

三个基本功一个不缺：**密钥从配置注入**（不硬编码）、**timeout=10**（不让一张图片拖死整个请求）、**raise_for_status()**（HTTP 4xx/5xx 立即暴露）。

拿到响应后不是原样返回，而是**裁剪成自己的形状**（第 43-50 行）：

```python
photos.append({
    "id": photo.get("id"),
    "url": photo.get("urls", {}).get("regular"),
    "thumb": photo.get("urls", {}).get("thumb"),
    ...
})
```

Unsplash 返回的原始 JSON 有几十个字段，这里只留五个——**服务层的输出是"我的数据结构"，不是"别人的数据结构"**。将来换图库，上层代码一行不用改。

`get_photo_url`（第 58-71 行）再往上包一层便捷方法："搜一张，取 URL，没有就 None"，正好对齐前端"一个景点配一张图"的需求。

## 🧅 洋葱心：MCP 调用的统一信封（amap_service.py 第 71-79 行）

```python
result = self.mcp_tool.run({
    "action": "call_tool",
    "tool_name": "maps_text_search",
    "arguments": {
        "keywords": keywords,
        "city": city,
        "citylimit": str(citylimit).lower()
    }
})
```

整个 `AmapService` 的五个方法，剥到底都是这**同一个信封**：`action` 固定为 `call_tool`，换 `tool_name`，换 `arguments`，完事。POI 搜索、天气、路线、地理编码——差异只在两个字段。

把它和智能体核心篇对照着看会很有启发：**同一个 MCP 工具，有两条使用路径**——

| 路径 | 谁决定调什么 | 形式 |
|---|---|---|
| Agent 路径 | LLM 决定 | 提示词里的 `[TOOL_CALL:amap_maps_text_search:...]` |
| 服务层路径 | 代码决定 | `mcp_tool.run({"action": "call_tool", ...})` |

前者灵活（模型按需取用），后者确定（程序精确控制）。一个成熟的智能体应用往往两条腿走路。

## 🎯 剥完之后：它在本章的位置

服务层是整个后端的"外交部"，三个外部世界各设一个大使馆：

| 服务 | 协议 | 被谁使用 |
|---|---|---|
| `llm_service` | OpenAI 兼容 API | 四个 SimpleAgent 共享（智能体核心篇） |
| `amap_service` | MCP（子进程） | `/api/map/*` 路由、`/api/poi/detail` |
| `unsplash_service` | REST | `/api/poi/photo` → 前端景点卡片配图 |

在"生成行程"的完整链路里，它们是**能力的提供方**：LLM 服务给流水线供"脑"，高德服务给行程供真实坐标，Unsplash 给结果页供颜值。上层只管调方法，密钥、协议、子进程这些俗务，全被关在这一层里。
