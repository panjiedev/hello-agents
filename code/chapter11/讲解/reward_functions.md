# 02_reward_functions.py 剥洋葱式讲解

> 源文件：`code/chapter11/02_reward_functions.py`（335 行）
> 一句话概括：**强化学习的"评分老师"——从二值的准确性奖励出发，用装饰器式组合叠加长度惩罚和步骤奖励，并剥开"从自由文本里抠出答案"这件脏活。**

---

## 🧅 第一层（最外层）：这个文件在干什么？

SFT 有标准答案可抄，RL 没有——模型自己生成解答，必须有人打分。**奖励函数就是那个打分的**，它是 RL 训练中唯一的"监督信号"来源：模型生成什么样的文本会被强化，完全由它说了算。

这个文件用 7 个示例回答三个问题：

1. 有哪几种奖励可选？（accuracy / length_penalty / step）
2. 打分的具体机制是什么？（提取答案 → 数值比较）
3. 不同奖励函数会把模型往哪个方向推？（示例 7 的对比实验）

设计奖励函数时刻记住一句话：**你奖励什么，模型就变成什么**——包括你没想到的钻空子方式（reward hacking）。这个文件的三种奖励正是围绕这个矛盾展开的。

---

## 🧅 第二层：三种奖励，三种价值观（第 21-107 行）

**准确性奖励**（第 31-34 行）——最朴素的价值观：

```python
config = {"action": "create_reward", "reward_type": "accuracy"}
# 答案正确: 1.0；答案错误: 0.0
```

二值奖励简单可靠，但有个隐患：它对"怎么答对的"毫不关心——答案是蒙的还是推理出来的，是 3 个字还是 3000 个字，得分一样。于是有了两个"修正价值观"的变体：

**长度惩罚奖励**（第 60-65 行）：

```python
config = {
    "reward_type": "length_penalty",
    "penalty_weight": 0.001,   # 每个 token 罚 0.001
    "max_length": 512
}
```

**步骤奖励**（第 92-97 行）：

```python
config = {
    "reward_type": "step",
    "step_bonus": 0.1,    # 每写一个推理步骤加 0.1
    "max_steps": 10
}
```

注意两者是**反向拉扯**的：长度惩罚说"别啰嗦"，步骤奖励说"多写推理过程"。选哪个取决于你要什么样的模型——要 API 省 token 就罚长度，要教模型思维链就奖步骤。权重的量级也讲究：`0.001/token` 意味着写 500 个 token 才抵掉 0.5 分——惩罚只应微调行为，**绝不能盖过 1.0 的正确性主奖励**，否则模型会学会"输出空串保平安"。

## 🧅 第三层：组合的秘密——奖励函数是可以套娃的（第 247-251 行）

示例 7 揭开了 `create_reward` 背后的构造方式：

```python
accuracy_fn = create_accuracy_reward()
base_fn = create_accuracy_reward()          # 基础奖励函数
length_fn = create_length_penalty_reward(base_fn, penalty_weight=0.001)
step_fn = create_step_reward(base_fn, step_bonus=0.1)
```

关键在参数表：`create_length_penalty_reward` 的第一个参数是**另一个奖励函数**。长度惩罚和步骤奖励不是独立的评分标准，而是**包在基础奖励外面的装饰器**：先调用内层函数拿基础分，再加减自己的修正项。这个模式的好处是可以任意叠加——理论上 `step(length(accuracy))` 就是"答对得分 + 鼓励步骤 + 抑制废话"三合一。

示例 7 用三个精心构造的样本验证价值观差异（第 254-270 行）：

| 样本 | 准确性奖励 | 长度惩罚版 | 步骤奖励版 |
|---|---|---|---|
| `"4"`（光秃秃的正确答案） | 1.0 | ≈1.0（短，几乎不罚） | 1.0（没步骤，不加分） |
| `"Step 1: 2+2=4\nFinal Answer: 4"` | 1.0 | 略降 | **>1.0**（步骤加分） |
| `"Let me think... "×20 + 答案` | 1.0 | **明显下降** | 1.0 |

同一个答案，三个分数——这张表就是"奖励函数即价值观"的实证。

## 🧅 洋葱心：从自由文本里抠答案（第 122-163、180-228 行）

奖励函数最脏也最关键的活，不是打分，而是**先从模型的自由发挥里找到"它到底答了几"**。示例 4 的测试样本暴露了模型输出的多样性：

```python
"Let me calculate: 2+2=4. Final Answer: 4"   # 规范格式
"The answer is 4"                             # 口语格式
"2+2 equals four. #### 4"                     # GSM8K 原生格式（#### 是官方答案标记）
```

`MathRewardFunction.extract_answer` 要能通吃这些格式（示例 5 还测了"藏在句中的数字"和"裸数字"）。提取失败就只能判 0 分——所以**答案提取的鲁棒性直接决定奖励信号的信噪比**，这也是为什么 SFT 阶段要先教会模型输出 `Final Answer: X` 的规范格式（见 04 篇）：格式稳了，RL 的奖励才准。

提取出来还要比较，而比较也有坑（第 210-219 行）：

```python
reward_fn = MathRewardFunction(tolerance=0.01)
("3.14", "3.14159", False),  # 超出容差 → 判错
("3.14", "3.141",   True),   # 容差内 → 判对
("100",  "100.0",   True),   # 字符串不等但数值相等 → 判对
```

字符串比较会把 `"100"` 和 `"100.0"` 判成两个答案——所以必须**转成数值再带容差比**。`tolerance` 是浮点世界的现实妥协：既要容忍 `3.14` ≈ `3.141` 的精度截断，又不能把 `3.14` 和 `3.14159` 混为一谈。

## 🎯 剥完之后：它在本章的位置

奖励函数是 GRPO 训练闭环里的"裁判席"：

```
prompt ──→ 模型生成一组解答 ──→ 奖励函数逐个打分 ──→ 组内比较算优势 ──→ 更新模型
                                   ↑ 本文件
```

`05_grpo_training.py` 默认挂载准确性奖励；想改变模型的"性格"（更简洁 / 更爱写推理），不用动训练代码，换个奖励函数即可。这是 RL 相对 SFT 最大的自由度，也是最大的风险点——**训练代码决定模型学得多快，奖励函数决定模型学成什么样**。
